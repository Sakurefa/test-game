Title: Population and goods economy chosen as the next gameplay priority
=========================================================================

The user stated a new high-level direction: before expanding the other world
domains, the project should first achieve a Victoria 3-inspired population
supply/demand system connected to goods production and consumption.

Repository review
-----------------

The current main baseline for this review was
`8284d16645fbd737dff2c5465a7f8507cea4521f`. The latest Windows Actions run
[44908873111](https://github.com/Sakurefa/test-game/actions/runs/44908873111)
completed successfully: syntax checks passed, npm test passed 172/172 with
zero failures, the Renderer build passed and the generated-renderer commit
step passed. This is automated CI, not a current user-side desktop test.

The current executable economy is still an aggregate first step:

- Each colony stores one scalar population total, a stockpile object, and
  industry instances.
- Commodity definitions can declare `daily_need_per_thousand`. Core only
  configures this for food and water; every resident in a colony is treated
  identically.
- Population needs are calculated daily and directly deducted from the
  colony stockpile. The system records requested, consumed, unmet quantity
  and satisfaction. Shortfalls do not yet alter population, health or
  stability.
- Industry recipes support multiple inputs and outputs. Weekly production
  is scaled by industry level, colony stability and available input stock.
  Recipe definitions already contain a workforce field, but the production
  formula does not use it and there is no employment or wage model.
- Markets are currently quote records associated with individual colonies.
  Commodity prices respond to the associated colony's stock relative to a
  target stock plus seeded random variation. There are no buy/sell orders,
  market clearing, household purchasing power or cross-colony goods flows.
- Existing stockpiles are shared colony-level inventories used by both
  industries and population consumption.

Useful foundations already in place include the INI content catalog and
cross-reference validation, saved world state and schema migrations,
daily/weekly scheduler with explicit dependencies, atomic candidate-day
settlement, deterministic named random streams, versioned formulas,
domain events, validated commands, read-only projections, autosaves and
player-readable production/needs reports.

The key conclusion is that the architecture can host this next economic
layer without replacing the engine or introducing a new framework. However,
the current data model and rules do not yet constitute a Victoria 3-style
population economy. The missing core is not merely more consumption rates:
it is differentiated population groups and needs, a model of income/
purchasing power, workforce and wages, explicit aggregate goods demand and
a market supply/settlement model that links production to consumption.

Design questions deliberately left open
---------------------------------------

No detailed rules were chosen in this review for cohort identity, wealth
bands, needs categories, substitute goods, affordability, labor allocation,
wage formation, market clearing, inventory ownership or exact daily/weekly
cadence. These must be discussed before implementation. Start with a small
coherent loop and do not import the entire scope of Victoria 3.

This entry records the user's priority and the audit result; it does not
authorize code changes or decide the detailed simulation model.

Title: The population model must remain moddable
=================================================

The user confirmed that the population economy should keep profession and
wealth as separate dimensions, then emphasized that the AK engineering
principle must be paired with a Mod-first content principle.

The practical boundary is now explicit: engine code should provide generic
simulation rules, while game-specific definitions and balance values belong
in Mod content. Core must contain the baseline INI definitions, and optional
Mods must be able to extend them. Profession lists, wealth tiers, need baskets,
consumption rates, wages and other economic content must not quietly become
hard-coded engine or Renderer data.

The first implementation slice therefore adds profession and wealth-tier
content types to the INI Mod loader/catalog and gives Core neutral placeholder
definitions. It does not invent a demographic composition, split any
existing colony population, or enable unfinished economic behavior.


Documentation correction
------------------------

During the final review, an update to the Mod API guide was mistakenly built
from a partial line-range fetch and briefly replaced the full guide with only
that excerpt. This was caught immediately by checking the committed diff.
The full guide was restored from the pre-change main revision, the intended
population section and save-compatibility wording were reapplied, and the
restored document was checked at its full 251-line length. No game runtime
code or save data was affected by this documentation correction.


Population-needs precision correction
-------------------------------------

The review confirmed a real sub-mill inventory defect: the daily needs
calculation rounded unmet quantity to three decimals, and the settlement layer
rounded actual consumption before deducting stock. A shortage of 0.0004 could
therefore disappear from the report while displayed consumption was rounded
above the actual available stock.

The fix keeps the requested-demand precision rule, preserves the exact actual
consumption and shortage values, and subtracts only the amount actually
available from stock. The colony needs panel now displays up to six decimal
places for these amounts. The population-needs formula version is raised to v2
so audit records identify the changed calculation behavior.


Precision regression-test correction
------------------------------------

The first CI run for population-needs v2 correctly caught stale assumptions in
the tests: a strict float equality, inspecting the input world rather than the
committed candidate returned by advanceDay, and old two-decimal UI expectations.
The implementation's new sub-mill renderer test passed. The failing assertions
were corrected to compare exact accounting with a tolerance and to expect the
intentional three-decimal display for the existing 1.175 example. The failed CI
run remains recorded in the work log.


Render assertion escape correction
----------------------------------

A second CI run showed that four renderer expectations still contained the old
two-decimal value. The attempted text replacement had matched a double-escaped
string rather than the single-backslash regex literals in the test file. The
four assertions are now directly replaced and checked in the retrieved file.
The engine-side precision behavior and the new sub-mill shortage regression
passed in that run.

Title: Confirming aggregate population and narrative individuals
===============================================================

The user made four explicit population-architecture decisions:

1. Population is simulated as aggregate groups, not as a population of
   continuously simulated individual people.
2. Group attributes initially store aggregate values, averages and proportions;
   do not build a complete joint distribution across every dimension.
3. Effects and date/condition triggers are separate concepts.
4. Population needs are settled for groups in aggregate, not person by person.

The user clarified the intended presentation boundary: ordinary residents
remain part of aggregate population statistics. Individual people appear only
when a narrative or strategically unique role makes them relevant, such as
an engineer featured in an incident or a named manager appointed to a key
building role. Such a person may have role-specific attributes and influence
a group or building, but this must not turn into a hidden individual-level
population economy. The character/group relationship and population-counting
semantics still need an explicit design before implementation.

The design must keep social class, profession, wealth, species/subspecies and
capability distributions independently extensible. Do not create every
possible cross-product of these dimensions. Marginal proportions cannot be
treated as proof of an intersection (for example, the share of highly capable
technicians) unless the model stores or derives that relationship. Class and
other content categories must come from Core/optional Mod INI definitions;
the engine must not recognize hard-coded class names or species-specific
gameplay rules.

The effect direction is to provide generic, targeted numerical influence with
an explicit source, target, operation and value. Permanent effects have no
timer; temporary effects use separate triggers for expiry or configured
follow-up actions. Trigger processing should work from due dates/conditions,
not by repeatedly scanning historical effects. This is a design contract,
not authorization to add specific laws, events, species, need values, wages
or other game content.

The next foundation direction is to define the smallest aggregate population
group representation and its independent statistical dimensions while
preserving the existing scalar colony population and legacy
`colony.population.delta` compatibility. Group-level needs and the effect/
trigger data contracts follow after that. The user explicitly reaffirmed the
AK principle and Mod-first content boundary: keep the engine generic, direct
and maintainable; put game definitions and balance values in INI Mod data.

Repository work in this session was limited to Astra's durable collaboration
records. No simulation code, Mod content, schema, tests, Renderer or game
balance values were changed.

Title: Personnel entities and deterministic settlement snapshots
===============================================================

The user clarified how named people relate to aggregate population:

- People are introduced through events. Ordinary hiring may create a selectable
  list of candidates abstracted from population groups; special events may
  introduce predefined or generated people.
- A separate persistent personnel pool stores already generated/acquired
  people serving the player (for example friends, partners or recruited
  personnel). Each personnel record may store profession and other role
  attributes, optional affiliations, and its own identity/relationships.
- A person may belong to a class/species/organization or other affiliation,
  or may have no normal population affiliation and serve independently.
  Exceptional entities such as royals and agitators may be managed in their
  own lists and appear at locations through their own mechanics.
- Personnel records are not a second population ledger. If a candidate is
  abstracted from a population group, the hiring/creation rule must explicitly
  define whether the aggregate group count is reduced. Do not double-count
  the person. No individual economic simulation follows from the personnel
  record.

The user also clarified the principle for conditional building effects:
avoid deriving frequently changing values from other frequently changing
averages or marginal percentages. Prefer direct operational data, especially
the building's actual employed workforce and headcounts. At a scheduled
settlement, inspect only the workforce attributes relevant to configured
conditions; skip irrelevant calculations when no employed group carries the
relevant trait/tag. Compute the qualifying share from actual employed people,
apply or remove the configured persistent building effect, then keep that
result unchanged through the interval. Staff changes during the interval do
not continuously invalidate the effect; the next scheduled settlement
re-evaluates it.

The user's intended coincident settlement priority is annual, monthly,
weekly, then daily. Weekly and daily are the ordinary current simulation
cadences; monthly and annual are future fixed-date settlement operations
invoked by triggers, not additional recurring scans. The thresholds, tags,
conditions and resulting effects remain Mod-defined INI content.

The resulting architecture principle is: direct source data over volatile
derived dependencies; calculate only relevant conditions; deterministic
settlement priority; stable effects between scheduled evaluations. No game
content or numerical thresholds were authorized by this clarification.
