经济系统设计
==============

目标：建立以人口群体为经济参与者的供需系统，并与商品生产、库存、市场价格和消费结算连接。长期希望呈现接近《维多利亚3》的宏观人口经济反馈，但不逐人模拟。

目前实现基础：
- 殖民地以人口群体人数作为权威人口数据；殖民地总人口是群体人数之和。标量 `population` 仅为派生兼容/读取投影，不是独立人口账本。
- Mod 可通过 INI 的 `population_group` 定义完整初始人口群体；没有群体定义时才由 fallback population 创建单一 `unclassified` 群体。
- 当前每日需求仍按派生的殖民地总人口聚合结算，需求来自 Core 商品定义中的 `daily_need_per_thousand`；它还不是逐群体需求。当前规则由 Core API v4 脚本执行，不属于 Engine 内置规则。
- Core 目前为食物和水配置基础需求；周度生产、日度需求、商品/证券报价和战争时间线均由 `mods/core/scripts/simulation.js` 提供行为实现，周期、顺序与依赖在 Core manifest 的 `[systems]` 中声明，参数仍在 INI。Recipe workforce 仍只是 metadata。
- 库存仍是殖民地共享库存；市场主要更新殖民地商品与证券报价，并非完整订单撮合或市场清算。

尚未决定：需求篮子、需求层级、替代商品、收入财富、购买力、商品分配、工资、劳动力供给、职业技能匹配、市场清算、库存所有权、跨殖民地物流，以及短缺对健康/稳定/迁移/出生/死亡的反馈。不得擅自补齐。

## Engine / Mod 边界修整（2026-11-23）

已将具体基线玩法从 Engine 移入 Core Mod：生产、殖民地总人口日需求、商品与证券定价、战争时间线由 Core 的 API v4 脚本负责；公式 ID/版本和 recurring system 的 cadence/order/dependencies/hook 在 Core manifest 声明；公式参数、商品/配方/货币/账户、初始资本和本地化文本保留在 INI。Engine 只提供公式执行与审计、Mod Hook 执行、系统 cadence/依赖调度、批准 Effect 执行、命名随机流和原子日结算。

当前 Core 的总人口日需求是过渡性既有玩法：仍不是群体 Need/Tag 匹配，也没有多个群体竞争共享库存的分配策略。不得将此实现误认为已经完成群体需求或分配接口；后续按已确认方向继续设计，由 Mod 决定短缺配额，Engine 不设置公平或 pro-rata 默认。

原则：群体级需求结算；经济内容与数值由 Mod INI 定义；显示不得改变计算精度；直接源数据优先于频繁变化的派生统计；先建立小而闭合、可验证的供需循环。

星际经济的世界设定约束（2026-11-23）
----------------------------------
- AI、仿生人和机械劳工是经济参与者。不同人口类型有不同需求：有机人口需要食物等生物物资；仿生人/机械劳工不需要食物，取而代之的是能源、精密部件和维护。具体需求包由 Mod 定义。
- 能源是世界经济最重要的结构性张力之一。恒星发电与技术发电都存在地点、设施和容量瓶颈；不同殖民地/星系争夺有限能源供应，能源市场不能被假定为无限供给的普通商品市场。
- 后续设计至少要区分发电潜力/装机能力、实际可供能源、消耗与分配、储能，以及可运输的能源载体。电力/功率、储能和燃料不应在没有契约前全部压成同一种库存数量。
- 星际航行、星门与混合运输方式均存在；不宜居星球也能殖民，但在不具备自然条件的地方实现食物等自给自足会非常昂贵。物流可达性和本地生产成本因此会共同影响殖民地经济。
- AI/自动化意味着生产能力不再简单正比于有机人口。生产模型最终要分别表达设备产能、劳动力需求、能源投入、原料投入和维护。
- 以上为已确认世界设定及长期设计约束。具体能源类型、设施、商品、配方、人口需求、运输成本和数值由 Mod INI 定义；当前阶段不提前实现能源市场、物流或具体玩法。

对现有地基的影响（仅作为边界，不是立即施工清单）
------------------------------------------------
1. 群体需求必须允许不同人口类型显式关联不同需求配置，不能把全部 Pop 当成同质消费者。
2. 库存受限消费与未来能源调度要区分；能源可能需要容量/持续供给语义，不能只依赖普通 stockpile。
3. 生产的 workforce metadata 不能被误认为已实现的劳动力模型；未来必须同时考虑自动化产能和真实雇佣人口。
4. 跨殖民地市场和物流尚未实现。市场价格、商品库存、运输中的货物、能源供应权/容量应是清晰区分的业务对象。


阶级生活水平、商品标签与市场相对品质（2026-11-23）
------------------------------------------------
用户提出的方向：采用阶级相关的 Need/生活水平设计。以食品为例，中高阶级可以接受高档或普通食品；若市场只能提供低档食品，数量需求可能得到满足，但其期望生活水平仍未满足，并产生相应不满。需求数量满足与品质/生活水平满足必须分别表达。

商品品质概念分层：
1. 商品属性/标签：商品可同时拥有多个 Mod-defined 标签，例如碳水、蛋白质；标签描述商品能提供什么，不等于商品名称或固定档次。
2. 标签品质贡献：不同标签可具有独立品质值或权重。多标签商品的综合品质由其标签贡献计算，具体聚合公式与权重尚未决定。
3. 生产修正：建筑、工艺或加工过程可以提高/降低最终品质；负面加工标签（例如垃圾加工食品）可作为明确的品质减损来源。品质计算仍属于待设计契约，不在 Engine 中硬编码具体标签或数值。
4. 市场相对档次：商品进入某一市场后，应与同一需求品类中可竞争的商品比较。相对档次是市场上下文中的派生判断，不是商品永久不变的固有字段；不同市场的竞争供给可能不同。
5. 阶级标准：Need Profile/阶级规则定义可接受或期望的商品档次。低档商品可以提供部分/全部数量，却未必满足较高阶级的品质标准。

必须保持的区分：
- 数量需求、标签/营养覆盖、商品品质、市场相对档次、价格/购买力和最终满意度不是同一个数值。
- 同一商品可以满足多个需求标签；不能假设所有标签对最终品质或需求贡献等价。
- 市场品质基准的统计口径仍未决定（例如市场供给量/成交量加权、候选商品集合及低流动性商品如何处理）。不能简单把动态市场平均值当作唯一绝对品质标准，否则单一商品市场可能自动把唯一商品视为“平均档次”。
- 若建筑/工艺能使同一 commodity ID 产出不同品质，而库存仍只保存该 commodity 的单一数量，品质差异会在入库时丢失。未来必须在商品变体、品质批次或其他明确库存表达中选择；当前普通 stockpile 尚不支持品质批次，本阶段不实现。
- 当前市场只有价格更新，不是完整订单撮合、购买力结算或市场清算。品质竞争/阶级消费属于后续设计，不得误写成已有功能。

本阶段先确定人口需求归属与共享库存分配的最小契约；商品标签品质、市场档次与支付能力应分层讨论，不把所有经济规则一次性塞进 Engine。


Tag 驱动的 Need 与商品品质设计（2026-11-23）
------------------------------------------
用户确认采用统一 Tag 方案，不建立专用 NeedProfile 内容类型。Need 规则通过人口 Tag 匹配；商品、营养成分、工艺与加工特征也通过 Tag 表达。

建议分层：
1. **人口 Tag**：描述物种、阶级、职业、法律身份及其他需求相关属性。不同概念保持语义独立。
2. **Need 规则 Tag 匹配**：Mod 定义规则适用的标签条件、需求类别、数量需求及档次期望。Engine 不硬编码有机/机械人口、阶级或商品名单。
3. **商品 Tag**：一个商品可同时具有碳水、蛋白质等标签；标签可带品质/营养贡献。建筑/工艺修正和负面加工标签影响最终商品品质。
4. **市场档次**：商品最终品质在具体市场、具体需求品类中与竞争商品比较后形成相对档次；不能将市场档次写成商品永久属性。
5. **需求结果**：数量满足、标签/营养覆盖、商品品质、市场档次、价格/购买力和最终满意度分开记录。

人口 Tag 匹配的统计约束：
- 当前 Pop Group 维度是独立边际分布，不是完整联合标签集合。
- 单一已保存维度可以直接提供对应人口份额；多维交集必须有明确保存的联合人口份额或显式细分群体。
- Tag 规则不得因为同时写了 species=organic 与 class=worker 就把两个边际比例相乘。
- 需要定义多规则匹配时的组合语义，避免同一人口份额被重复计算或因文件顺序产生差异。

共享库存分配候选方案（待用户确认）：
- 对每种商品分别汇总所有人口需求份额的请求量，再根据该殖民地当前共享库存进行分配。
- 第一版建议采用按该商品请求量比例分配（pro-rata）：库存足够则全额满足；库存不足则所有请求方对该商品获得相同的数量满足率。这样不会因 Pop/Need 定义顺序而产生隐含优先级。
- 每个人口需求份额分别记录 requested、allocated/consumed、unmet 与 quantity satisfaction；殖民地报告再汇总。品质/生活水平满足单独计算，不能把低档商品的数量消费当成高档需求已满足。
- 该候选规则暂不引入阶级优先级、财富购买力、货币支付或商品替代。若未来需要优先级，应由明确的 Mod 规则定义，而不是迭代顺序。
- 浮点余数处理、跨需求类别共享商品的分配口径，以及 Tag 匹配冲突仍需在契约设计阶段闭合。

能源仍只作为边界案例：Tag/Need 规则可以描述能源维护需求，但电力功率、持续供给、容量、储能、传输与普通库存商品的消费语义不能混为一谈；本阶段不实现能源基础设施。


共享库存分配：策略由 Mod 决定，Engine 保留接口（2026-11-23）
----------------------------------------------------------
用户明确纠正：不能把按需求比例分配（pro-rata）称为公平，也不能把它设为 Engine 默认策略。财权阶级较高的殖民地公民可能拥有更高获取配额；购买力、财富、阶级特权、配给制度、政治关系等都属于具体游戏经济规则，应由 Mod 内容决定。

职责分层：
1. **需求生成**：Engine 根据人口数量与可用人口标签/Need 规则计算需求请求；具体规则由 Mod 定义。
2. **分配策略**：Engine 提供可扩展的策略接口/调用边界，由 Mod 选择并定义商品短缺时的分配方式。不得硬编码平等、按比例、阶级优先或其他分配意识形态。
3. **库存执行**：Engine 负责对策略返回的分配结果执行库存扣减，并维护一致的请求、分配、短缺和满足记录。

接口契约至少需要明确：输入需求请求与可用库存；输出按请求方/人口份额和商品标识的分配数量；如何处理未覆盖请求、无效/超库存/超请求分配、数值精度和确定性；如何把结果归档到群体级与殖民地级报告。Engine 可执行通用数据合法性与库存守恒检查，但不能擅自重写策略结果来实现某种公平标准。

Pro-rata 仅可作为某个 Mod 自行选择的策略示例，不是 Engine 默认值，也不应成为隐藏 fallback。若没有可用分配策略，系统应有明确的配置/运行错误或显式的无分配语义，具体待接口设计决定；不得悄悄退回按比例分配。

本阶段只设计接口，不实现具体阶级配额、购买力、支付、市场清算或任何具体分配制度。
