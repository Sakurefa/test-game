关于接下来的工作
==================

当前阶段是通用 Engine 地基与 Mod 边界建设，不是直接扩张具体人口经济玩法。所有可运行的游戏内容都由 `mods/` 下的 Mod 提供；`mods/core` 是必需的基础内容 Mod，本身不属于 Engine。Engine 负责可复用的数据表示、装载、验证、调度、结算、持久化与扩展接口；具体分类、实体定义、规则参数和玩家文本由 Mod INI 提供，需要程序化表达的行为由 API v4 明确声明的 JS Hooks、Formulas 与 Simulation Systems 提供。

已完成的 Engine 地基：
1. World schema 9 的通用聚合人口群体存储。**人口群体的人数是权威人口记录；殖民地总人口等于所有群体人数之和。**标量 `population` 仅作为兼容/读取投影，由 Engine 从群体重新汇总，不是另一份人口账本。每组包含稳定 ID、人口数量和独立统计维度；每个维度内部比例合计为 1，不同维度不生成隐含联合分布。
2. Mod INI 初始群体声明契约。Mod 注册 `population_group`，使用 `colony_id`、`population` 和 `dimension.<id>` 定义群体。只要任一启用 Mod 为殖民地声明群体，这些群体就构成完整初始人口，其人数之和直接定义运行时总人口；不要求与 colony 定义中的 fallback `population` 相等，不额外补 `unclassified`。只有完全没有群体定义时，才从 colony `population` fallback 创建一个中性群体。
3. 人口群体运行时变更契约。旧 `colony.population.delta` 继续表达真实总人口增减：正增量进入 `unclassified`，负增量按现有人群比例扣减，操作后重新汇总总数。新增 Mod Effect 支持群体拆分、合并和维度分布更新。拆分/合并不改变殖民地总人口，且沿用现有 `mod.effect-applied` 记录路径。
4. 查询投影 `colony.summary` 提供群体快照，并从群体汇总总人口；派系摘要同样取派系殖民地的人群总数。现有需求系统仍只消费派生总人数，无需理解群体维度。

## 已确认的通用触发/结算设计与实现状态

这组设计不是新的提议，已经记录在 `Astra/WORKING_MEMORY.txt` 第 7、9 节、`Astra/DISCUSSIONS/人员与建筑结算设计.txt`，以及 `Astra/WORKFLOWS/2026-11-21_03_clock-observability-save-integrity-and-population-foundation.txt`。

核心约定：
- **效果与触发器分离。**效果描述对世界数值的影响；触发器决定何时发生、何时到期或何时调用动作。
- 永久效果不需要计时器。临时效果由独立触发器处理到期/变化；触发器可以结束或改变效果、发出事件或调用经过批准的动作。
- 时间推进时处理已经到期的触发器，不扫描全部历史效果。
- 通用数值影响需要来源、目标、运算类型和值；按业务语义支持加、减、乘等操作。
- 建筑条件读取实际雇佣群体与人数，而非从人口平均值或独立边际比例推算交叉数据。只在约定结算点计算需要的属性与人数比例，并让结果在下一结算点前保持稳定。
- 多个周期性 simulation systems 在同一边界到期时，固定顺序为 **年度 → 月度 → 周度 → 日度**。年度/月度由 registry cadence 按真实日历日期判定；周度按每七个经过日，日度按每个完整游戏日。
- 周期性 system cadence 与单个持久化 Trigger instance 是两种不同职责：前者负责重复运行的系统结算；后者负责单次日期/经过时间/条件/领域事件动作，以及临时效果到期。Trigger Queue 不应复制 annual/monthly recurring scheduler，也不应维护另一套日历算法。

## 历史实现状态（截至 2026-11-22_03；保留当时状态用于追溯）

已存在的底层：
- campaign clock、暂停/倍速和日期/日分数推进。
- simulation system registry：支持 annual、monthly、weekly、daily、manual 五种 cadence；年度按 1 月 1 日、月度按每月 1 日判定，周度仍按每七个经过日；同日顺序固定为年度 → 月度 → 周度 → 日度。系统 ID、order、依赖排序、同步执行和上次执行日记录仍沿用原机制。当前实际注册的游戏系统仍只有周度生产与日度人口需求、市场定价和战争时间线。
- 当前真实结算顺序：每七日重合时，周度生产 → 日度人口需求 → 日度市场定价；战争时间线日度推进。
- 固定 Mod Hook：campaign.before-day/after-day、colony.before-production/after-production、market.before-pricing/after-pricing、war.after-chronology。
- 命令分发器、主进程命令网关、Domain Event 历史与只读事件总线。
- 版本化计算服务与计算审计；目前注册四个专用公式：population-needs、colony-production、commodity-price、security-price。

仍未实现的机制：
- 通用触发器定义/注册/持久化/到期队列，以及条件与事件驱动触发。月度/年度 cadence 的调度基础已实现，但当前尚无实际注册的月度或年度游戏系统。
- 通用条件/阈值求值，以及由日期、条件或领域事件触发的游戏动作。
- 触发器到已批准动作/效果/命令的通用调用契约。当前命令分发与事件总线各自存在，但没有由通用触发器调用它们的规则通道。
- 通用来源/目标/运算/数值影响层；目前是逐个硬编码并校验的 Mod Effect 类型，不是可组合的通用数值修改器。
- 临时效果状态及其到期/变更触发处理。
- 建筑实际雇佣 workforce 数据、结算快照与条件效果稳定期；目前 recipe workforce 仍是 metadata，没有可供这些条件读取的真实就业数据。

容易误判的示例：
- `mods/example-market` 的“monthly observation”Hook 注册在 `campaign.after-day`，每日被调用，再用 `input.day % 30 === 0` 自行判断。这是 Mod 脚本模拟每 30 个经过日观察一次，不是 Engine 的月度日历调度器。
- Domain Event Bus 的订阅者收到的是已发生事实的只读快照；Mod 自定义事件不会自动触发其他子系统的状态变更。
- 现有公式服务虽可注册确定性计算并记录输入/步骤/修正/随机抽取/结果，但四个公式目前由 Engine 代码实现；它不是 Mod 可定义的通用效果运算或触发器。
- `runManual` 只允许显式执行登记为 manual 的模拟系统，不等同于日期/条件/事件触发器。

这表示上一轮把下一项概括为“人口阈值触发”过窄。人口规模阈值只是通用触发机制未来的一个消费者，不是整套设计的起点。

## 2026-11-22_03 推进结果：日历结算 cadence 第一阶段

## Cadence 与 Trigger instance 的边界（2026-11-22）

这一边界用于约束下一阶段实现，不代表通用 Trigger System 已经完成：

1. **Recurring cadence 归 simulation system registry 管理。** Annual、monthly、weekly、daily 是重复结算系统的调度规则；manual 仍只接受显式调用。它们不应该被复制成每个 Mod/每个 Trigger instance 的重复任务。
2. **Persisted Trigger instance 表示单个待执行动作。** 它面向一次性日期动作、经过时间到期、条件/领域事件响应，以及临时效果的独立到期动作。永久效果不需要对应的 timer。
3. **共享同一战役时钟。** 日期触发读取 `world.clock.date`，日历校验与日期运算复用 `engine/clock.cjs` 的规则；不另造月份长度或 30 天近似。现阶段经过时间只在完整 campaign-day 边界结算，因为 `dayFraction` 目前只是日内时钟进度，没有子日模拟结算。
4. **与每日原子结算绑定。** 到期动作、触发器出队和由动作产生的领域事件都先写入 candidate world；只有整日成功后才一起提交。失败时丢弃 candidate，不允许出现动作已应用但触发器仍被移除，或触发器已出队但动作未应用的半完成状态。Event Bus 只在 world commit 后接收新事件。
5. **只调用批准动作。** Trigger record 只引用明确登记并校验的 Effect/Command/Event 入口；不能存放任意 JS 函数、任意 Mod 回调或任意 world patch。

## 2026-11-22_09 Trigger System 第一阶段 Engine 实现

本次将此前的事件概念明确为两种不同对象：
- **System Event**：Trigger 到期后创建的短生命周期内部处理请求，由 Engine 注册的 Resolution 接收；不是面向玩家的叙事/通知。
- **Domain Event**：已经发生的事实，保存于 `world.domainEvents`，并在 world commit 后通过只读 Event Bus 发布。
- Presentation 后续可以根据处理结果和已提交事实生成通知、报告、图标或弹窗；本阶段不实现表现层。

第一阶段实际实现：
1. World schema 升为 9；旧 schema 1–8 迁移时初始化空 Trigger Queue，保留其他已有世界数据。
2. `world.triggerQueue` 保存待处理 Trigger 与最近处理回执；支持 `date` 和 `elapsed` 两类整日 due condition，日期校验/日数计算复用 `engine/clock.cjs`。
3. Mod API v4 hooks 可返回有限数量的 `triggers` 描述。Owner 由 Engine 从 Hook 所属 Mod 注入；Trigger ID 必须以该 Mod ID 为前缀。相同定义去重，不同定义复用 ID 报错。
4. Trigger 的待处理项按 dueDay、稳定 ID 排序，只处理到期项。已存在于队列中的 due Trigger 在每日结算开头执行：时钟推进之后、`campaign.before-day` 之前，因此早于全部 recurring cadence systems。
5. Hook 在本日结算中创建的 Trigger 不会在本次被重新扫描；最早下一个完整 campaign-day 边界执行，避免同一结算内递归触发。
6. 内部 System Event 首期只注册 `effect.apply` Resolution。它调用 Engine 现有的 `applyModEffect`；在调度时先用候选副本验证一次，实际到期时再次验证并应用。没有开放任意 JS handler、命令分发器或 world patch。
7. 成功处理会在候选世界写入 `mod.effect-applied` 与 `trigger.resolved` Domain Event、从 pending 队列移除并记入最近回执；回执保留最新 256 条。相同 ID 的永久去重不在本阶段承诺。
8. 触发执行、效果变化、Domain Event、出队和回执都在 `advanceDay` 的 candidate world 内；任一步失败，正式世界保留原待处理 Trigger，整日候选被丢弃。

本阶段仍未实现：条件/阈值来源、Domain Event 驱动来源、Command/Event Resolution 类型、通用数值 modifier、临时效果生命周期以及 UI Presentation。也没有加入人口、建筑、经济等具体玩法。

第一阶段源码 Windows CI 已通过：[44949943031](https://github.com/Sakurefa/test-game/actions/runs/44949943031)，215/215 tests、语法检查和 Renderer build 全部成功；Electron 存档 schema 9 写入/旧版读取边界也已接通。
下一步建议：先明确 Resolution/Settlement 的“结果计算”与“Effect 执行”契约，再根据真实数据和消费者决定第二个通用 Resolution。条件触发、Domain Event 驱动、随机结算池与 UI Presentation 应分别设计，不要为了完整感一次性扩大框架。
## 2026-11-22_10 Resolution 结果计划与 Effect 执行分离

本次在已实现的 Trigger System 上继续补齐执行边界，不新增具体游戏规则：
1. 所有 Resolution 必须返回 `{ result, effects }`；结果对象与有序 Effect 描述数组通过 JSON-safe 结构校验，Effect 最多 16 项。
2. Resolution 只计算并生成计划，不负责修改 World。Trigger Runner 单独调用已有的 Effect 执行入口，逐项执行已注册 Effect，并记录 `mod.effect-applied`。
3. Trigger 成功后写入的 `trigger.resolved` 同时记录 Resolution result 和已应用 Effect 的结果；计算失败或任一 Effect 失败都回滚整个 candidate day。
4. 新增第二个真实消费者 `formula.effect`：只调用已有 Engine 公式注册表，输入是调度时保存的 JSON-safe 快照；Mod 提供有限 Effect 模板，以简单的顶层 `resultFields` 映射公式输出字段。它不新增公式语言，也不开放任意 JS resolver。
5. 公式随机抽取使用由 Trigger ID 派生的独立命名随机流，计算记录和随机流状态沿用现有 candidate-world 提交路径。

当前边界：不允许 Mod 注册公式/Resolution 函数；不支持嵌套字段路径、算术表达式、条件表达式或动态世界对象引用；Effect 仍必须通过现有 Mod Effect 白名单。Formula 输入数据是调度时快照，不是到期时实时读取。

## 2026-11-22_11 Settlement 执行管线从 Trigger Queue 抽离

本次继续把调度与执行职责分开：
1. 新增 `engine/settlement.cjs`，提供通用 `settleSystemEvent()` 入口。
2. Settlement 接收一个 System Event、detached candidate-world snapshot、Resolution registry 和 Effect executor；它返回结算结果与实际应用的 Effect 结果。
3. Settlement 不操作 Trigger Queue、不写 Domain Event history、不接触 Presentation/UI。
4. Trigger Runner 只负责检测 due item、创建 System Event、调用 Settlement、写 `trigger.resolved`、出队和 receipt。
5. Effect executor 仍是 Engine 注入的既有 `applyModEffect`；Settlement 不暴露任意 Mod callback。
6. 测试独立覆盖 detached snapshot、Effect 单独改变 candidate world、零 Effect resolution 与异步 Effect executor 拒绝；现有 Trigger 集成测试继续验证整日原子事务。

本次只是将已有一条实际执行路径抽成可复用 Engine 模块，没有新增存档字段、触发源、Effect 类型或具体玩法。CI 结果以工作流记录 2026-11-22_11 为准。

## 2026-11-22_12 实现结果：Domain Event 驱动的单次 Trigger

本次在现有 Trigger Queue 与 Settlement 之上，新增第三种 due source：`domain-event`。

- Trigger 订阅一个精确 Domain Event type，可选精确 scope 和 subjectId。
- 仅观察订阅创建之后新写入的事实；不读取/扫描 bounded Domain Event history，不回放历史，不支持 payload predicate、wildcard 或自动重复订阅。
- 新事实写入 candidate world 时，Domain Event emitter 检查待处理 Trigger Queue 并激活匹配项。Pending Queue 仍受 4096 条上限约束。
- 命中后保存来源事件 JSON-safe snapshot，并设定 dueDay = sourceEvent.day + 1。当天不执行；下一完整日边界使用既有 System Event、Settlement 和 Resolution 链。
- Source snapshot 随 Trigger receipt 与 `trigger.resolved` 保存，因此 Domain Event history 后续淘汰旧记录不会丢失这次触发的来源上下文。
- Event Bus 继续只在 candidate world 成功提交后发布事实，不承担 Trigger 激活或权威状态变更。
- 未新增 World schema 字段；schema 保持 9。既有 date/elapsed Trigger 的定义、签名和处理规则保持兼容。

## 2026-11-23：阶级 Need、商品品质与市场档次方向

用户补充的需求设计方向已纳入本阶段设计：
- 阶级与生活水平标准相关。不同阶级对需求品类和商品档次有不同接受范围；数量消费满足不等于生活水平满足。
- 商品可有多个标签（例如碳水、蛋白质），不同标签具有不同品质贡献；生产建筑/工艺可改变品质，负面加工标签可降低品质。
- 商品进入具体市场后，与该市场同一需求品类的竞争商品比较，形成市场相对档次；Need Profile/阶级标准再判断该档次是否满足期望。
- 商品固有/批次品质、市场相对档次、阶级期望、需求数量和满意度必须分开。标签品质聚合公式、市场基准统计口径与品质库存表示尚未确定。

下一步设计要点：
1. 先明确 Pop Group 的 Need Profile 人数如何被准确表示。可考虑独立的显式 need_profile 分布，使类别比例直接代表需求群体人数；不能通过 class、species、profession、wealth 等独立边际相乘推算联合人口。最终契约需结合用户既有阶级设计确认。
2. Need Profile 可表达需求品类、数量需求与可接受/期望档次；具体档案、标签、商品映射、数值仍由 Mod INI 定义。
3. 群体共享库存分配必须有确定性规则，并分别报告数量满足与品质/生活水平满足；分配优先级、公平性和短缺结果仍待设计。
4. 商品标签品质、市场相对档次、市场价格/购买力应是不同层次。当前阶段不扩张成完整市场撮合或支付系统。
5. 若生产修正能造成同一商品不同品质，未来库存需保留品质来源；本阶段只记录该约束，不实现批次库存。

明确延后：品质批次库存、商品替代与完整购买力/支付、订单撮合/市场清算、跨殖民地物流、能源发电容量与调度。先把 Pop 需求归属和殖民地共享库存分配契约设计闭合。

## 2026-11-23：共享库存分配策略归属（用户已明确）

用户明确：短缺时谁获得多少是游戏内容/经济制度设计，不是 Engine 应替玩家决定的公平原则。不得把 pro-rata、平等配给、阶级优先或其他分配原则硬编码为 Engine 默认。

## 2026-11-23：Engine 与 Mod 边界修整结果

4. 新世界的货币、初始账户、玩家账户归属和开局资金由 Mod INI 定义。通用账本只做整数最小货币单位、交易平衡、账户和转账机制。旧 CR/player-main/系统财政初始化已隔离为专用 legacy-save migration 路径，不用于新世界创建。
5. 玩家可见的新世界名称、世界创建文本和每日系统结算摘要来自 Core localization INI。地点类型与战争状态使用 Mod 稳定 ID，不再使用 Engine 的封闭枚举；舰队状态与战争状态不在 Engine 内填充游戏默认值。
6. Mod 的 Domain Event type 使用 `mod.<mod-id>.<local-event-type>` 命名空间。Core UI 只在表现层去除自身 Mod 前缀以复用既有文案映射。

本次不是把底层代码塞进 Core：`engine/` 仍提供调度、公式执行与审计、Effect 执行、随机流、Trigger、Domain Event 和原子 Settlement；Core 脚本属于可替换的具体基线游戏行为。现阶段 Core 的人口需求仍为总人口聚合模型，不是群体 Tag Need，也没有群体间库存分配。下一阶段继续完善 Tag/Need 与 Mod 分配策略接口的设计，不加入 Engine 默认分配意识形态。

## 2026-11-23：种族维度优先的 Pop Group / Need 方向修正

用户明确纠正：Pop Group 的分类重点是不同种族/物种，而不是把有机、仿生、合成、机械劳工划分为 Engine 预设类型。项目现行方向：
- 使用现有 Mod-defined `species` 人口维度作为种族分类示例；各个种族 category ID 和语义由 Mod 定义。
- 不为任何生命形态或种族在 Engine 中建立硬编码实体类型/需求表；种族名称本身不自动决定需要什么商品。
- Need 由 Mod-defined Tags / rules 决定。一个维度内的多个类别可以精确 OR 匹配；跨独立维度的交集仍须明确人口份额，禁止相乘。
- 先完成单维度人口份额匹配基础，再闭合 Tag 映射、Need 规则重叠与联合人口表达。不要先造全局 Tag Catalog、NeedProfile 实体或其他无当前消费者的抽象。
