## Project identity

- Repository: [Sakurefa/test-game](https://github.com/Sakurefa/test-game)

- Game: moddable multi-system frontier simulation.
- Stack: Electron + Chromium + Vite + Node.js.
- Current phase: extensible multi-domain simulation foundation. The engine has continuous campaign time, modular daily/weekly systems, named RNG/formulas, domain events, trusted command dispatch, authoritative finance balances, structured diagnostics, rotating autosaves, atomic day settlement, mixed INI/JavaScript Mod hooks, per-Mod persistent state and read-only world queries. Keep the implementation direct: many explicit attachment points, but no abstract framework without a concrete consumer.

## Modding/runtime capability boundary

- API v3 remains INI-only. API v4 adds explicitly declared JS hook functions while all content data stays INI.
- Current built-in hooks cover campaign day boundaries, colony production, market pricing and war chronology. Current approved effects cover colony population/stability/stockpiles, market quote multipliers, fleet readiness/morale, war weariness and Mod-owned state set/increment/delete.
- Each Mod has its own saved state namespace (schema 7), 128 keys and 64 KiB. Hooks can only see their own modState object; the global state table is removed from the script-facing world projection.
- The engine exports detached query projections for world overview, faction, colony, market, fleet and war. The renderer still uses the older snapshot IPC and has not yet migrated to the query registry.
- The VM wrapper is not a security boundary for hostile code. Never claim arbitrary downloaded JS Mods are safe. Treat scripts as trusted/opt-in until process-level sandboxing exists.

## Non-negotiable decisions

1. **Mod content is INI; optional behavior is JavaScript through API v4.** Manifests, registry declarations, entity definitions and localization remain INI. API v3 data-only Mods stay supported. API v4 may declare simple files under scripts/ and named hooks. JSON Mod files and inline JSON values remain forbidden. Root npm package metadata and internal game-save serialization are not Mod content.
2. **Localization is separate.** Names, descriptions, government labels, commodity units and other player-visible text live in locale INI files. Content refers to stable localization keys; do not embed translated display text in definitions.
3. **Stable IDs are language-independent.** IDs are machine-facing and must not be translated.
4. **Mod JavaScript uses a narrow effect contract.** Hooks receive detached frozen JSON snapshots, deterministic helper functions and only their own persistent state; they return approved effects/events. They never receive mutable world references, arbitrary command execution, Node/Electron services, filesystem/network access, native modules or host callbacks. The current Node vm wrapper reduces capabilities but is not a hardened boundary against deliberately hostile code; JS Mods are trusted/opt-in until a real OS process sandbox exists.
5. **Core is required and always enabled.**
6. **Distribution model:** the repository contains the complete editable game source and Electron runtime files; the standalone launcher EXE is distributed separately (for example through the user's QQ group), not committed to the repository. The launcher loads the game from its adjacent repository directory.
7. **Do not claim tests passed unless they actually passed.** CI, local checks and user-side Windows testing must be reported separately.
8. **Machine-first engineering:** the program executes defined work and records what happened; it is not an autonomous agent that must constantly inspect or repair itself.
9. **Runtime state is authoritative.** Current balances and world variables are the state used by the simulation. Diagnostic logs are evidence for external maintenance, not a second state database that must be replayed to answer ordinary runtime queries.
10. **Record causes, not just outcomes.** Important operations should log source module/entity, operation ID, campaign time, inputs, relevant calculation values, result and error context. Logs should make player-reported bugs searchable and reproducible.
11. **No full-history audit on ordinary operations.** Full validation belongs at load/migration or explicit diagnostic boundaries. Normal execution performs only the checks required for that operation; it must not repeatedly replay all past transactions or scan the whole world without a concrete need.
12. **Prefer direct code and proven seams.** Do not add generic layers, lifecycle hooks, checkpoint schemes, self-healing or defensive machinery without a demonstrated use case. Preserve real boundaries such as trusted main-process IPC and atomic file writes.
13. **Diagnostic logs may be large, but bounded.** Use searchable line-oriented records and rotating/archived files. The user accepts hundreds of MB of logs; do not truncate useful diagnostic history merely to keep logs tiny, but never allow unbounded disk growth.

## Current world prototype

The initial world is the Helios frontier:
- Four systems: Solace, Cinder, Eos and Veil.
- Three colonies and three factions.
- Commodities, production recipes, markets, companies/securities, fleets, wars and events.
- Market/security quotes and war chronology update daily; colony industrial production is scheduled every seven elapsed game days (day 7, 14, 21…).
- This is a prototype, not yet a full logistics, colony management, trading, financial or RTS implementation.

Long-term direction:
1. Deepen colonies: population demand, labor, maintenance, facilities, stability and expansion.
2. Implement actual interstellar logistics: freighters, cargo orders, route capacity, travel time, risk and stock transfers.
3. Build company economics and player finance: balance sheets, cash flow, trading, positions, credit and dividends.
4. Build strategic warfare: fleet movement, supply, front lines, territory, war goals and faction AI.
5. Separate real-time tactical combat from strategic world time.
6. Add dynamic events, diplomacy and systemic world changes.

### 2026-11-21 — fix continuous clock display synchronization and renderer overhead

- User reported a concrete runtime defect: the day progress percentage only changed after clicking a speed button; world panels also appeared stale, and the game felt sluggish.
- Read the complete root `AGENTS.md` and `ASTRA_WORKLOG.md`, checked current `main` and the latest successful CI run before investigating. Starting main head: `de2bfeefba5981ec3ae9f2b8fd48268e590bcb18`.
- Root cause: the renderer's polling code read `state.world.clock.day`, but the actual snapshot shape is `state.world.world.clock.day`. This threw before it could update the stored snapshot or display, so the periodic refresh silently aborted in its catch handler. Speed-button actions appeared to fix the display because they returned a fresh full snapshot and explicitly rerendered the screen.
- Second issue: the old 500 ms poll invoked `world:time-status`, which constructed and serialized a full world snapshot even though the UI only needed the clock fraction. This caused avoidable IPC and repeated catalog/snapshot work.
- Added `world:clock-status` in Electron main and a narrow preload API `getClockStatus()`; it returns only the campaign clock, time-control state, save ID and dirty marker. Full `getStatus()` snapshots are now requested only when the authoritative day count changes and daily simulation systems have committed.
- Added `src/time-display.mjs` with a pure interpolation helper. Renderer uses `requestAnimationFrame` to smoothly animate the progress percentage/bar between authoritative clock samples. It clamps the predicted display at 99.9% until the main process confirms the day boundary, so visual interpolation cannot invent a calendar day or mutate simulation state.
