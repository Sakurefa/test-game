【最高优先级重要原则】MOD 化原则
=====================================

本原则与 AK 原则并列，是本项目内容架构、引擎边界和社区扩展的最高优先级约束。任何新游戏规则或内容都必须先判断是否应由 Mod 定义，不能因为写进引擎更方便就硬编码。

核心目标：引擎提供稳定、通用、可复用的模拟机制；游戏内容、规则定义与平衡数据尽可能由 Mod 提供。Core Mod 是基础游戏内容包，其他 Mod 在既定接口内扩展内容。玩家应能在不修改引擎源代码的前提下调整和创建游戏内容。

一、引擎与内容分离
- 引擎实现通用机制、数据装载、校验、结算与扩展接口，不直接承载具体游戏设定。
- 商品、资源、配方、建筑、职业、阶级、物种、亚种、需求、工资、价格基准、效果、标签、事件、法律、派系及平衡数值等原则上由 Mod 定义。
- 不把 Core 的具体内容名称、规则和平衡常量硬编码进 Engine、Renderer 或 Electron 主流程。
- 引擎可以定义通用字段、运算符、结算机制和系统约束；具体定义与数值由 Mod 注册。
- Renderer 展示游戏状态，不成为游戏规则的权威来源。

二、Mod 内容格式
- Mod manifest、registry、内容定义和 localization 使用 INI。
- 不得以 JSON 文件或内嵌 JSON 值替代 Mod 内容配置。
- 根目录 package.json 等 Node/Electron 构建工具元数据不属于 Mod 内容，不受此限制。
- API v3 INI-only Mod 必须继续兼容。
- API v4 可在明确声明的 scripts/ 与 hooks 接口中使用 JavaScript 扩展行为；不得借此把本应由 INI 定义的内容、分类和数值搬回脚本。
- 不得把任意 JavaScript 当作普通 Mod 内容脚本执行。

三、注册、引用与本地化
- Mod 内容通过 registry/catalog 等既有机制注册，使用稳定 ID。
- 内容之间通过稳定 ID 或明确引用关联，不依赖显示名称或文件顺序。
- 玩家可见文字放在 localization INI，以稳定 localization key 引用。
- 不在引擎和 UI 中散落硬编码的玩家可见内容文本。
- Core 是必需基础 Mod，不允许被禁用；依赖和加载顺序遵循现有 Mod 系统契约。

四、扩展边界与安全
- Mod API 只暴露明确列出的能力。脚本读取脱离权威运行时对象的只读快照，只返回经过注册与校验的效果或事件。
- 不向 Mod 暴露任意 Node/Electron API、文件系统、网络、原生模块、可变世界对象或任意宿主回调。
- 当前 Node vm 包装属于能力收敛，不是抵御恶意 JavaScript 的强安全沙箱；JavaScript Mod 应视为可信/用户主动启用内容，不得宣称可安全执行任意不可信脚本。
- 不为 Mod 扩展建立与引擎状态并行的第二套权威世界状态。
- 新扩展能力应有明确使用场景和契约，不因“社区也许会需要”而开放过宽接口。

新增游戏定义或规则前自问：这是通用机制还是具体内容/平衡？若是内容，是否应进入 mods/core 或独立 Mod？是否需要新的 INI 字段、registry 类型或稳定 ID？玩家可见文本是否使用 localization key？现有 API 是否已能表达？若不能，是否确有必要扩展引擎？是否保持向后兼容且足够小？

默认选择：通用机制留在引擎，具体内容与规则定义进入 Mod INI。
