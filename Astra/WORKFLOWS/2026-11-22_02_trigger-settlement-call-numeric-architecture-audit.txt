已记录的设计事实
----------------
工作记忆第 7、9 节及 2026-11-21_03 工作流早已记下：
- 效果与触发器分离。
- 永久效果不需要计时器；临时效果由独立触发器处理到期/变化。
- 到期触发器可以结束/改变效果、发出事件或调用经过批准的动作。
- 时间推进只处理到期触发器，不扫描全部历史效果。
- 通用数值影响应有 source、target、operation、value；按语义支持 addition、subtraction、multiplication。
- 建筑条件使用实际雇佣群体与人数，不从平均值或独立边际比例推导交叉统计。
- 在配置的结算期只检查条件需要的数据，按实际雇佣人数计算比例，应用/移除效果，并让效果在下一结算点前保持稳定。
- 周期重合的顺序为 annual → monthly → weekly → daily；月度/年度未来通过固定日历日期触发，而不是后台持续扫描。
- 这些属于明确设计方向，不是对具体职业标签、阈值、建筑效果或游戏平衡的批准。

当前实现状态
------------
已实现的通用底层：
- campaign clock、日期与日分数、暂停/倍速。
- system registry 支持 daily、weekly、manual；稳定 system ID、order、dependsOn、拓扑排序、同步更新、每个系统的 lastRunDayBySystem。
- 当前周日重合顺序：weekly colonies.production → daily population.needs-consumption → daily economy.market-pricing；military.war-chronology 日度运行。
- 已定义固定 Mod Hook：campaign.before-day/after-day、colony.before-production/after-production、market.before-pricing/after-pricing、war.after-chronology。
- 已存在显式 command dispatcher、world command runtime、主进程 command gateway；当前玩家网关实际注册的命令只有 finance.transfer。
- 已存在 typed Domain Event 历史与 Event Bus。Event Bus 将已发生事实交付给只读订阅者，不是游戏状态触发器。
- 已存在版本化公式计算服务和审计记录，当前四个 Engine 公式：economy.population-needs、economy.colony-production、economy.commodity-price、economy.security-price。
- 已存在若干逐项定义的 Mod Effects；每种效果的 payload 与合法性规则由 Engine 单独登记。

尚未实现：
- 通用 trigger 定义/注册/持久化/到期队列。
- 条件/阈值求值及日期、条件、事件驱动的通用游戏动作。
- 真实日历月/年 cadence 和 annual → monthly → weekly → daily 的统一结算顺序。
- 从触发器到经批准的 effects/commands/events 的通用调用契约。
- 通用 source/target/operation/value 数值影响层；当前是逐类型硬编码 Effect，不是可组合的通用数值 modifier。
- 临时效果持久化、到期、变更和移除流程。
- 实际就业群体数据及建筑条件结算快照；recipe workforce 当前只是 metadata。

特别澄清的反例：
- example-market 的 monthly-market-observation Hook 实际挂在 campaign.after-day；每天调用 JS，代码用 `input.day % 30 === 0` 判断。它是每 30 个经过日的示例脚本，不是真实日历月 scheduler。
- Domain Event 的 subscriber 只能观察已提交事件快照；MOD_API 明确指出自定义事件不会自动改变其他子系统。
- Hook 只在 Engine 固定列出的调用点执行；Mod JS API 只给 random/clamp/round，不提供任意 command invoke 或通用 effect registry。
- formula service 可记录输入、步骤、修正、随机抽取和结果，但具体四个公式仍由 Engine 代码定义，不能等同通用数值影响系统。
- runManual 是对手动注册模拟系统的显式调用，不是日期/条件/event trigger。

下一项建议（尚未获代码施工授权）
------------------------------
应按整体机制审查并制定最小契约：
1. trigger lifecycle：日期、经过时间、条件与事件触发；到期队列、持久化、去重、失败边界；只处理 due 项。
2. settlement periods：真实日历月/年及 annual → monthly → weekly → daily 顺序，与已有 daily/weekly 系统兼容。
3. approved invocation：触发器如何调用经过批准的 Effect、Command 或 Event；不开放任意 Mod 函数或任意 world patch。
4. numeric influence：source、target、operation、value；永久/临时效果生命周期；计算公式与效果应用分离。
5. 用实际已确认的通用消费者作验证；建筑 workforce 条件须等真实就业数据存在后再做完整验收，人口阈值可以是简单消费者但不能代替基础设施。
