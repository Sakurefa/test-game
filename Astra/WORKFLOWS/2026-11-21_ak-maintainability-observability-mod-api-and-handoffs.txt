### 2026-11-21 — architecture and maintainability audit (read-only review)

- Re-read the complete root `AGENTS.md` and the complete current `ASTRA_WORKLOG.md` before this review. Confirmed the current `main` head before this log update was `f0c75a9978a45c0293b6ce12cf5d2434e1145620`; the immediately preceding source revision is `8fe1f8324db1c8abda8c2b8834349fe165aad3a6`.
- Inspected the current source and architecture documentation, including `engine/system-registry.cjs`, `engine/clock.cjs`, `engine/campaign-time.cjs`, `engine/commands.cjs`, `engine/command-runtime.cjs`, `engine/event-bus.cjs`, `engine/domain-events.cjs`, `engine/ledger.cjs`, `engine/simulation.cjs`, `engine/index.cjs`, `electron/world-command-gateway.cjs`, `electron/main.cjs`, `electron/storage.cjs`, `package.json` and `docs/ENGINE_ARCHITECTURE.md`.
- Overall assessment: the project has **not** become an enterprise framework. The authoritative engine remains plain Node.js/CommonJS, the simulation is not coupled to Electron/DOM, modules are mostly ordinary functions and explicit state objects, there is no class hierarchy/DI container/external runtime dependency, and the Mod boundary remains data-only INI. The clock and system registry are relatively small and understandable. This is a sound foundation for the user's simple/reliable/maintainable/modifyable engineering goal.
- Confirmed maintainability deviations and risks:
  1. Several recently added core files use heavily compressed one-line formatting, especially `commands.cjs`, `ledger.cjs`, `domain-events.cjs`, `event-bus.cjs`, `command-runtime.cjs` and `world-command-gateway.cjs`. This reduces review/debugging readability without providing a meaningful runtime benefit. New and touched core code should use normal readable formatting; gradually reformat touched modules rather than performing a risky repository-wide churn.
  2. Command execution currently traverses gateway -> command runtime -> dispatcher -> handler, then domain-event persistence -> event bus. These are individually understandable boundaries, but only `finance.transfer` is registered. Treat this as a necessary security seam, not a reason to add more generic wrappers; do not add layers unless a second real use case demonstrates the need.
  3. `recordBalancedTransaction` validates the full ledger, clones the full ledger, appends, then validates the full candidate ledger again. `validateWorldState` also replays the complete ledger through `validateWorldFinancialState`; it is called by day advancement, snapshots and command validation. Cost therefore grows with transaction history and can become expensive when financial simulation becomes high-volume. This is a concrete future scalability issue, not a current measured slowdown. Add a verified checkpoint/segment strategy or separate cheap runtime invariants from full integrity audits before enabling frequent trading; do not weaken correctness.
  4. JSON-safe cloning/normalization and deep-freezing helpers are implemented separately in command, event-bus and domain-event modules. Review whether a tiny shared utility is justified when those paths next change; avoid introducing a general utility framework merely to eliminate a few lines.
  5. The system registry exposes initialize/save/restore/dispose hooks, but current registered simulation systems only use update, and the simulation runtime currently calls runDue. Keep lifecycle hooks only if they are part of an imminent concrete save/load lifecycle; otherwise avoid expanding speculative lifecycle machinery.
  6. The command dispatcher makes multiple structured clones of the whole world for read-only guards, execution drafts and post-transition validation. This provides useful isolation/atomicity today, but its cost scales with world size. Measure before adding more clone boundaries and consider narrower immutable views only when correctness can be preserved.
  7. `advanceDay` advances the clock and mutates systems directly on the live world. If a system update throws after an earlier system has changed state, the day may be left partially applied. This is a reliability concern to address with a small, explicit day-settlement transaction/rollback boundary before adding many more systems.

### 2026-11-21 — machine-first engineering and full maintainability audit

- Re-read the complete root `AGENTS.md` and complete `ASTRA_WORKLOG.md` before review. Current `main` head: `4d1aaa54d82478aef6cf253c4e03f3206d51be33`. Latest GitHub Actions run [44829395527](https://github.com/Sakurefa/test-game/actions/runs/44829395527) completed successfully. Its syntax, full test, renderer build and generated-renderer steps all passed; the available job summary does not expose a test count.
- User clarified the governing engineering philosophy: the game is a machine, not an AI. Prefer straightforward execution plus complete diagnostic records and external maintenance. Runtime variables are authoritative; logs are diagnostic evidence and must not be replayed or referenced to maintain ordinary state. Avoid continuous self-auditing, self-repair machinery, speculative abstractions and redundant validation. The user accepts large logs (hundreds of MB) provided they remain useful and bounded.
- Inspected the current repository tree and the main engine/runtime path: `engine/ledger.cjs`, `commands.cjs`, `command-runtime.cjs`, `event-bus.cjs`, `domain-events.cjs`, `simulation.cjs`, `system-registry.cjs`, `clock.cjs`, `campaign-time.cjs`, `random.cjs`, `formulas.cjs`, `catalog.cjs`, `electron/logger.cjs`, `bootstrap.cjs`, `main.cjs`, `preload.cjs`, `storage.cjs`, `world-command-gateway.cjs`, `mod-loader.cjs`, `ini-parser.cjs`, renderer world/audit/refresh modules, package scripts, CI workflows and the relevant engine/storage/command/ledger tests.
- Overall assessment: the project is still plain Node/CommonJS with no DI framework, no class hierarchy for the simulation, no external runtime dependency and a clean engine/Electron/renderer boundary. The core is not broadly over-engineered. The main mismatch is concentrated in repeated state validation, the finance ledger's full-history model, and diagnostic logging that is currently much less complete than the user's desired maintenance workflow.
- **Confirmed high-priority defects and mismatches:**
  1. `electron/logger.cjs` lines 50 and 52 use the literal escaped sequence `\\\\n` in the written record instead of an actual newline. Runtime and startup entries are therefore concatenated onto one physical line, defeating normal line-based log reading/search. The current logger test checks file existence/content but does not assert line boundaries.
  2. Disk logs are not complete simulation diagnostics. The engine has no logger dependency/callback. The gateway's wildcard event subscriber logs only event ID/type/day/subject ID and drops event payloads. Calculation traces are retained only in a 200-record in-save buffer; domain events retain 300; narrative events retain 100. These bounded save histories are not a substitute for the external diagnostic log the user described. No player-facing diagnostic export/package flow was found in the inspected UI.
  3. Fatal process handlers in `electron/bootstrap.cjs` log `uncaughtException` and `unhandledRejection` but do not terminate or otherwise mark the process as failed. Installing these listeners suppresses Node's default fatal handling, so the app may continue after an uncaught failure with potentially inconsistent state. Log, then terminate safely for truly fatal exceptions rather than silently continuing.
  4. `advanceCampaignTime` calls `validateWorldState` on every campaign timer callback. The Electron timer ticks every 100 ms, so this runs up to ten times per second while time is advancing, even when no whole game day elapsed. At a day boundary, `advanceDay` validates the world again. `createSnapshot` also performs full validation. This is unnecessary hot-path work.
  5. `validateWorldState` calls `validateWorldFinancialState`, which replays every ledger transaction. Consequently the full finance history can be replayed on each 100 ms time tick, each day settlement, snapshot generation and command validation. This is broader than the previously documented “new transaction” cost.
  6. `recordBalancedTransaction` validates the entire ledger before append, clones the entire ledger, then validates the full candidate again. It also scans all transactions to detect duplicate command IDs. Account/currency registration repeats whole-ledger validation and cloning. This makes ordinary financial operations depend on the entire historical ledger and duplicates state in the save.
  7. `advanceDay` mutates the live world directly: it advances the clock and then runs systems sequentially. If a later system throws, earlier mutations remain. The campaign timer catches the exception and pauses time, but the partially advanced world remains active and may still be saved. This is a real failure boundary to address; it does not require a self-repair framework.
  8. The current runtime log cap is 25 MiB per file with three archives (roughly 100 MiB of runtime history plus up to 25 MiB startup log), and each individual record is truncated at 64 KiB. This is more restrictive than the user's accepted diagnostic-log budget. More importantly, `appendFileSync` writes synchronously on the Electron main thread; increasing log detail without changing the write path could stall simulation/UI.
- **Design observations (not all are defects):**
  - The financial ledger currently treats its append-only transaction array as the accounting source of truth and the balance as a replay-verified projection. This is directly contrary to the clarified user preference. The likely target is direct authoritative integer balances plus external transaction diagnostic records. The ledger may be simplified or removed after all references and schema migration paths are mapped; do not delete it blindly.
  - There are several different histories with different purposes: `world.events` (player-facing narrative feed), `domainEvents` (typed in-world event records and event-bus delivery), `audit.calculations` (formula traces), and `Logs/runtime.log` (process diagnostics). Their roles are not clearly separated. Keep actual gameplay history where needed, but move developer diagnostics to disk logs and stop treating bounded in-save debug traces as the main support channel.
  - The gateway -> command runtime -> dispatcher -> handler path has several layers, but the trusted main-process boundary and renderer actor derivation are valuable. Keep the security boundary; avoid adding more generic wrappers. The dispatcher currently clones the whole world for guards/drafts/validation, which will become expensive as the world grows; narrow this only when a concrete safe alternative is available.
  - The registry's initialize/save/restore/dispose hooks are currently unused by registered systems. They are speculative surface area; do not add more lifecycle behavior unless a real system needs it.
  - The event bus's detached immutable snapshots and subscriber error isolation are useful at the module boundary, but do not confuse them with persistent diagnostic logging.
  - INI-only, data-only Mod loading and the Electron-main authoritative world boundary remain aligned with project requirements. No need to introduce entity frameworks, generic resource systems or other speculative abstractions during this cleanup.
- **Recommended correction order:**
  1. Fix line-oriented logging and add tests that assert separate records; correct fatal exception handling; add a useful diagnostic record schema and log actual simulation/transaction calculation inputs and outcomes. Keep engine independent from Electron by passing a small optional logging callback or recording at the existing main-process event boundary.
  2. Remove full `validateWorldState` calls from the 100 ms fractional-time path and read-only snapshot path. Keep full validation at save load/migration and explicit diagnostic/test boundaries; retain cheap local checks where an operation actually needs them.
  3. Simplify financial state: balances are authoritative integer variables; transaction detail is recorded to the diagnostic log. Remove full historical replay, full-ledger cloning and the 50,000-transaction runtime ceiling if no longer needed. Before changing schema, map all uses of `finance.transactions`, `positions`, command IDs and legacy migrations.
  4. Give daily settlement a small explicit failure boundary so a failed system cannot leave a half-applied day that can be saved. Prefer a simple transaction/working-copy boundary over generic rollback infrastructure.
  5. Revisit whether calculation traces and typed domain-event persistence need to remain in the save, distinguishing player-visible world events from developer diagnostics.
- No source code, tests or build files were changed during this audit. No local tests or builds were run. CI result is the existing successful run [44829395527](https://github.com/Sakurefa/test-game/actions/runs/44829395527); it verifies the current committed code only and does not mean the identified issues are fixed. No Windows GUI test was performed or requested.

- Next concrete task: implement the diagnostic logging correction first (actual newlines, fatal error behavior, detailed simulation/transaction records and tests), then remove repeated full validation from high-frequency paths. Revisit the finance schema only after the logging path can preserve the transaction facts needed for external debugging.

### 2026-11-21 — diagnostic logging, authoritative finance, autosaves and fail-fast simulation

- Work started from the then-current main baseline and the full root AGENTS.md / ASTRA_WORKLOG.md were reread before implementation. Source implementation head for this batch: 1b229fa0296f39dc60f181d80c16c14e39da70a7. The work is on PR #1 pending merge at the time of this entry.
- Logging: Replaced malformed escaped line endings with one JSON object per physical line (JSONL). Records carry ISO timestamp, level, scope and structured payload. Nested Errors preserve name/message/stack/cause chains; circular references are made printable. Runtime logs rotate at 100 MiB per file and retain four archives (active + four archives, approximately 500 MiB maximum runtime history); individual records are accepted up to 16 MiB. The startup log remains bounded. Logger writes stay synchronous so fatal records are on disk before the fatal report is assembled.
- Diagnostic detail: The Electron main-process event subscriber now writes complete typed domain-event payloads. Each completed day writes a detailed simulation record containing game day/date, production summary, market summary, executed systems and all formula calculation records generated during that day. Finance transfer events include command ID, source/destination account, currency, amount, transaction sequence/ID and resulting balances.
- Finance simplification: Account integer balances are now authoritative runtime state. A transfer checks only the transaction inputs and affected accounts, applies the balance deltas directly and returns a diagnostic fact for the event log. It no longer clones the whole ledger, replays transaction history, scans old command IDs or appends every transaction to an in-save history. Legacy transaction arrays remain readable/ignored for compatibility; they are not used to calculate current balances. Full finance validation checks current currency/account structure and balances, not historical replay.
- Validation frequency: Removed full-world validation from the 100 ms campaign clock tick and read-only snapshot path. Removed full-world post-command validation from the gateway. Full validateWorldState remains on save load/migration. Day entry performs targeted checks for required world identity, clock/RNG/scheduler/event state, colony population/stability/industry recipe and level, market references/prices, fleet/war state and player finance. Required missing/zero/invalid values throw errors with the affected entity ID.
- Atomic day settlement: A day is calculated on a detached candidate world and committed only after all due systems finish. If a simulation system throws, the candidate is discarded and the live world remains at the previous completed day. System update errors are rethrown with the failing system ID and SIMULATION_SYSTEM_FAILURE.
- Fatal handling: Campaign-time, manual-day, snapshot/clock-reference and internal command-handler/commit failures pause and unload the active world. Renderer returns to the title menu and shows a fatal dialog with the failure source/message and a copyable text area containing the matching JSONL error record plus up to five surrounding records from the active log and rotated archives. Process-level uncaught exceptions/unhandled rejections are logged and terminate the process rather than continuing in an unknown state.
- Autosaves: Added electron/autosave.cjs. Every completed game day queues a daily autosave; days divisible by seven also queue a weekly autosave. Each cadence owns two rotating slots: slot_auto_daily_1/2 and slot_auto_weekly_1/2. Slot 1 is newest; slot 2 is the previous snapshot. The queues serialize writes and are tracked during shutdown. If a player loads an automatic slot and manually saves, a separate slot_manual_* is created so the automatic rotation is not overwritten.
- Files changed: electron/logger.cjs, electron/bootstrap.cjs, electron/autosave.cjs, electron/main.cjs, electron/preload.cjs, electron/world-command-gateway.cjs, engine/ledger.cjs, engine/simulation.cjs, engine/system-registry.cjs, engine/commands.cjs, engine/command-runtime.cjs, package.json, src/main.js, src/styles.css, tests/autosave.test.cjs, tests/commands.test.cjs, tests/engine.test.cjs, tests/ledger.test.cjs, tests/storage.test.cjs, tests/system-registry.test.cjs, docs/ENGINE_ARCHITECTURE.md, docs/PLAYTEST_GUIDE.md.
- CI: GitHub Actions run 44836971873 succeeded on Windows Server 2025 / Node 22. Syntax checks passed, npm test passed 115/115 tests, and npm run build:web passed. This is CI verification, not a user-side GUI test.
- Not performed: No local test/build run and no user Windows GUI test. The daily/weekly slot rotation, loading an autosave then manual saving, fatal modal copy interaction and deliberately injected runtime failure still require a combined Windows desktop playtest.
- Known boundaries: Autosaves occur after completed game-day boundaries (weekly additionally on day 7, 14, 21, ...); they do not create an initial save before the first day settles. Runtime log writes are synchronous and individual lines above 16 MiB are replaced by a diagnostic-size warning record. Renderer-process termination is logged; process-level fatal main-process failures terminate rather than attempting to continue. The current UI has not yet been Windows-tested for the fatal modal.
