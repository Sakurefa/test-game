## 工程边界
- 项目仍处于通用 Engine 地基阶段。Engine 提供机制、数据装载、验证、结算、持久化和受限扩展；全部可运行游戏内容由 mods/ 提供。mods/core 是必需基础 Mod，不属于 Engine。
- Mod manifest、registry、内容和 localization 保持 INI；API v3 INI-only 兼容；API v4 JS 仅限声明式 hooks 与批准结果。
- 遵守 AK 原则与 MOD 化原则：简单可靠、只为真实消费者抽象、避免重复权威状态；不提前建设通用框架。

## 当前实现概览
- 世界数据：多星系/星域空间内容、殖民地、市场、舰队、战争等基础定义；Catalog 交叉引用验证；World schema 9，旧 schema 1–8 迁移到 9。
- 时间与模拟：战役时钟、暂停/倍速时间推进、annual/monthly/weekly/daily/manual simulation cadence；当前实际游戏消费者为周度生产、日度人口需求、市场定价与战争时间线。没有实际 annual/monthly 游戏系统。
- 执行与扩展：detached candidate-world 日结算与原子提交、命名随机流、版本化计算审计、命令运行时/主进程网关、Domain Event history、post-commit read-only Event Bus、Mod API v4 hooks。
- Trigger：持久化队列；date、elapsed-day、new Domain Event 三类来源；effect.apply、formula.effect、event.emit 三种 Resolution；13 种批准的即时 Mod Effect；独立 Settlement runner；整日 candidate-world 原子性和回执。核心实现与自动化模拟验收完成。条件/阈值来源、Command Resolution、通用 Modifier/临时效果生命周期和 Presentation 未实现；没有真实消费者前不应继续扩展。
- 财务：玩家账户与整数最小货币单位账本、转账命令等基础能力；并非完整税收、债务、公司财务或市场结算系统。
- 生产与市场：殖民地每周按 recipe/industry level/stability 结算生产，输入受库存约束；每日更新商品/证券报价。不是完整跨殖民地订单市场或物流。
- 人口：World schema 9 的聚合 populationGroups 为权威人口数量；殖民地 scalar population 是派生兼容投影。Mod 可通过 INI 定义完整初始群体；运行时支持群体 split/merge/维度更新。群体维度是独立边际，不推导联合分布。
- 需求：当前每日仍按殖民地总人口 × commodity.daily_need_per_thousand 计算；共享殖民地库存受限消费并记录 requested/consumed/unmet/satisfaction。尚无群体需求归属、群体间库存分配、购买力/工资或需求替代。
- 建筑就业：recipe.workforce 只是 metadata；没有实际雇佣群体、建筑 workforce 人数、工资或就业结算。
- 世界物流：星际航行/星门是世界设定方向，但当前没有舰队移动、货物运输、跨殖民地物流或人口迁移系统。

## 已确认的世界经济前提
- 有机生命 Pop 需要食物等生物需求；仿生人和机械劳工 Pop 不需要食物，转而需要能源、精密部件与维护。AI/机械劳工意味着生产能力不能简单等同于有机人口数量。
- 能源是最大的经济张力之一：恒星发电与技术发电受位置和容量限制，殖民地/星系争夺有限能源。未来必须区分发电能力、实际供给、消耗分配、储能和可运输能源载体；当前没有能源系统。
- 可进行星际航行、建立星门并混合使用；不宜居星球也可殖民，也可培养食物，但不适宜环境下的自给自足成本极高。以上是世界设定，不代表物流、能源玩法已实现。

## Pop 归属与流动的设计约束
- 概念关系：势力提供政治管辖/组织视图；殖民地是当前居住地与现有人口群体权威存放位置；建筑是工作地点，通过就业分配关系引用群体和人数。
- 人口只保留一份权威数量。势力统计与建筑 workforce 都是派生/引用关系；建筑雇员仍属于殖民地人口，不得双重计数。
- 当前所在地、政治归属、来源/籍贯、雇佣关系、所有权是不同关系。机器人制造来源和所有权可有意义，且可与当前殖民地、势力、雇主不同。
- 移民/调拨是跨殖民地守恒转移；出生/制造和死亡/报废改变总量；失业只改变就业；政权更迭只改变管辖；所有权转移不自动改变位置或人数。
- 这些是未来设计约束，不是当前实现，也不批准立即增加全球人口账本、产权系统或迁移框架。

## 下一步方向与边界
上一轮 Trigger 完成后的建议尚未被实现：推进人口群体级需求与商品消费。当前实现检查确认它仍未开始，群体需求配置与共享库存分配均未落地。

建议下一次工作流按以下顺序：
1. 先设计最小需求配置契约：群体如何显式关联需求配置，使有机人口与合成人口能拥有不同需求；具体配置与商品映射仍由 Mod INI 提供。
2. 明确如何从独立人口维度获得需求归属，禁止通过边际比例相乘推导 species×profession 等交叉人口。显式 profile 引用或直接需求归属维度只是候选，不预设答案。
3. 定义多个群体竞争殖民地共享库存时的分配规则，以及群体结果如何汇总为殖民地报告；保持确定性、可解释、可审计。
4. 能源作为设计边界案例考虑，但不直接实现能源市场、发电容量或跨星系能源物流；保留未来功率/容量与库存能源的区别。
5. 设计确认后再实现最小闭环与聚焦测试。具体种族、商品、需求数值和人口比例仍由 Mod 提供，不写入 Engine。

暂缓：人口来源分布、跨殖民地移民/机器人调拨、所有权、政治身份分离、实际建筑就业关系及工资。它们已作为设计约束记录；只有在群体需求/库存分配形成稳定消费者，或出现真实 workforce/迁移消费者时再设计和实现。建筑就业不能靠人口边际比例推算。
