人口系统设计
==============

已确认：人口采用纯群体模拟，不为普通居民建立持续运行的个人记录；群体属性先保存聚合值、平均值与比例，不建立完整联合分布；需求按群体聚合结算；效果与触发器分离。核心原则：群体是模拟实体，个体是叙事实体。

群体维度可包括阶级/阶层、职业、财富、物种、亚种、能力与资格分布。定义与类别由 Mod INI 提供，不在引擎硬编码。

禁止隐式交叉组合：不能将独立边际比例相乘来推断交叉比例。只有模型实际保存组合关系或从直接业务数据统计得到，才能使用交叉比例。避免全维度笛卡尔积。

权威关系：人口群体的人数构成殖民地总人口；总人口等于所有群体人数之和。运行时 scalar `population` 仅作为兼容/读取投影，由 Engine 从群体重新汇总，不得作为另一个权威人口来源，也不得用它反向推算或分摊群体。旧 `colony.population.delta` 保留总体增减语义；正增量进入未分类群体，负增量按现有群体人口比例扣减。当前 profession 与 wealth_tier 只有中性占位，尚无实际 Core 人口构成。

仍未决定：需求篮子的具体结构、替代品、支付能力及需求不足对人口的后续影响。不得提前加入具体阶级、物种、工资、需求规则或人口比例。

当前 Engine 实现状态（2026-11-22）
-----------------------------------
World schema 8 已加入通用持久化 `populationGroups`。每个群体的人数是权威人口记录；殖民地总人口由所有群体人数求和。scalar `population` 只保留为 Engine 重算的兼容/读取投影，不是另一份权威账本；存档与日结算边界检查它与群体总和一致。群体包含稳定 ID、人数和独立维度类别比例；不同维度不推导联合分布。

初始化时，若至少一个启用 Mod 为殖民地定义群体，则这些群体构成完整初始人口，总人数就是各群体人数之和；不按殖民地配置的 fallback 标量反推或补齐，不叠加默认群体。只有完全没有群体定义时，才从旧 colony `population` 配置生成单一 `unclassified` 群体。schema 1–7 存档迁移时，也只在首次迁移中将旧 scalar 总量转换为中性群体；迁移后以群体为准。

旧 `colony.population.delta` 已兼容：正增量进入 `unclassified`，负增量按现有群体人数比例扣减，之后从群体重新汇总总人口。通用 Mod Effect 还可拆分/合并群体和设置群体维度；这些群体重组操作不改变殖民地总人口。当前每日需求仍按派生总人口聚合结算，尚未改成逐群体需求；Core 仍没有写入实际人口构成或平衡数值。

Mod INI 初始化契约与当前实现（2026-11-21）
-------------------------------------------
通用 `population_group` 内容类型已接入 Mod loader、Catalog 与新世界初始化。Mod 使用 `[population_group.<stable-id>]` 段，并在 registry 中用 `[entry.<same-id>]` / `type = population_group` 注册。字段为 `colony_id`、非负 `population`，以及零个或多个 `dimension.<dimension-id>` 分布。每个维度用 `category-id:proportion` 列表表示，比例总和必须为 1。

同一殖民地在所有启用 Mod 中声明的群体人数共同构成该殖民地完整初始人口；Engine 将这些人数求和作为运行时总人口，不要求它们等于 colony 配置中的 fallback `population`，也不会在其外追加默认群体。只有完全没有群体定义时，Engine 才从 colony `population` fallback 创建单一 `unclassified` 群体。职业与财富维度的分类 ID 分别引用对应的 profession / wealth_tier Catalog；其他维度使用通用稳定 ID。人口群体是内部初始化数据，不强制要求玩家可见名称。

空的 populationGroups Catalog 集合不加入内容指纹，以保持既有 schema 8 存档在没有新增人口群体内容时的兼容性；一旦 Mod 声明了实际群体，定义就进入正常内容指纹，保存的世界仍绑定对应 Mod 内容。

本次只通过测试 Mod fixture 验证数据装载与初始化，没有在 `mods/core` 写入任何实际人口组成或比例。当前 Core 没有人口群体定义，因此新世界才使用中性 fallback；其他 Mod 一旦声明群体，就由群体人数总和定义完整初始人口。每日需求仍按派生殖民地总人口聚合结算，并非群体级需求。

群体运行时变更契约（2026-11-22）
--------------------------------
- 拆分：从一个已有群体转移一部分人数到新的稳定 ID；数量必须大于 0 且小于来源群体人数，殖民地总人口不变。未指定结果维度时，新旧群体沿用来源分布；若要指定拆分后的两套维度，必须同时提供，且每个独立维度的各分类人数在拆分前后守恒。
- 合并：将来源群体全部并入目标群体并移除来源 ID；两组必须具有相同的维度集合，每个维度按两组人数加权合成比例；殖民地总人口不变。没有单独的“删除有成员群体”操作。
- 维度调整：替换指定群体一个维度的类别比例，不改变该组人数和殖民地总人口。是否以及何时发生重分类由 Mod 规则决定，Engine 只负责数据变更与合法性验证。
- 三类操作通过已注册 Mod Effect 提交，沿用现有 `mod.effect-applied` Domain Event 记录 Mod、hook、原始输入和实际结果；不引入第二套状态或事件溯源。
- `colony.summary` 只读投影暴露群体数据和由群体汇总的总人口。需求、规模限制等只需要总量的系统继续使用该汇总值，不必理解群体维度。

种族/物种差异与人口 Need（2026-11-23，按用户最新修正）
-----------------------------------------------------
Pop Group 的人口分类轴应是 **Mod 定义的不同种族/物种**，不是 Engine 预设的有机、仿生、合成或机械生命形态分类。

- 现有 `species` 是普通 Mod-defined population dimension。Mod 负责声明使用哪些种族类别 ID、每个类别代表什么，以及它们关联哪些 Tag / Need 规则；Engine 不预设人类、外星人或其他种族列表，也不根据名称推断生物形态或需求。
- 不同种族可以拥有不同需求，但具体需求属于 Mod 规则。任何种族是否需要食物、能源、精密部件、维护或其他商品，都不能由 Engine 固定推断。
- Species、profession、class/social status、wealth、legal status 等维度各自表达不同事实。需求规则只匹配 Mod 明确提供的标签/分类依据。
- 一个 Pop Group 的单一维度分布直接表达该维度各类别的人数份额。匹配同一维度中的一个或多个类别（类别之间互斥，按 OR 合并）可以精确计算人数。
- 不同维度是独立边际分布。若规则同时要求不同维度的交集，必须有明确保存的联合人口份额或显式细分群体；绝不能把独立比例相乘推算交集。
- 生产能力、劳动力、自动化、能源输入与维护是不同业务概念，不得从种族 ID 或总人口直接推导；将来若实现，仍由 Mod 提供业务定义并以真实数据为依据。
- 能源供需可以是战略瓶颈，但特定种族是否拥有能源 Need 仍由 Mod 决定；电力/功率、储能、运输载体与普通库存消费的边界另行设计。

人口归属、所在地与流动的长期约束
--------------------------------
- 当前 populationGroups 存在于殖民地状态中，群体人数构成该殖民地人口；尚无独立的世界级人口所有权/迁移账本。
- 未来概念关系为：势力提供政治管辖/组织视图，殖民地是当前居住地，人口群体是权威聚合人口记录；建筑只通过就业分配关系引用群体与人数，不另存一份人口。
- 当前所在地、政治归属、来源/籍贯、雇佣关系、所有权是不同关系。不能把一个 factionId 或 ownerId 字段当成它们全部。
- 来源地可用于群体统计，但不要求给普通人口建立个人档案。任何群体的制造/来源、登记来源或所有权都必须由具体 Mod 按真实需要定义；不得预设这些关系只属于某种生命形态。
- 移民/调拨应跨殖民地守恒转移人数；出生/自然增长、机器人制造属于人口新增；死亡、报废、永久离开模拟世界属于人口减少。失业/离职只改变就业分配；政权更迭只改变政治管辖；所有权变更本身不改变人口所在地或数量。
- 这些是后续设计约束，不代表现在批准新增 world schema、迁移系统或产权系统。普通居民继续采用聚合模拟，特殊人员继续使用独立人员池并防止双重计数。

下一阶段仍先处理群体级需求与共享库存分配。人口跨殖民地迁移、来源分布、所有权和建筑就业引用关系暂缓实现；但需求配置设计不得破坏上述边界。


物种、阶级与需求归属（2026-11-23）
--------------------------------
- 沿用现有 Mod-defined species 人口维度表达不同种族；具体种族类别和含义由 Mod 定义。Engine 只处理通用 Pop Group，不预设种族列表，也不将人口区分为有机、仿生、合成或机械等固定生命形态类型。
- Species/种族分类是可供 Need Tag 规则匹配的人口属性，但不自动推导具体需求。Species、职业、阶级/阶层、财富和法律身份分别表达不同事实；奴隶身份不是物种。所有类别及其含义由 Mod 定义。
- 阶级生活水平与需求配置有关：阶级可以定义对需求品类、商品档次的接受范围/期望标准；实际需求不能只用一个“是否消耗了某商品”的布尔值表示。
- Need Profile 必须有明确人口归属。若某个需求配置只取决于一个已经保存的维度，可以从该维度直接得到对应人数；若需求同时取决于阶级、物种等多个独立维度，则必须由 Mod/人口数据显式保存对应的需求归属或联合群体，禁止把独立边际比例相乘来猜测交叉人数。
- need_profile 作为显式需求归属维度，是当前设计阶段的候选表达：其类别直接指向 Mod 定义的 Need Profile，分布比例直接表示各需求群体的人数份额。它是人口群体中的真实统计分配，不是由 class × species 等边际推导出的结果。最终 INI 字段与运行时契约仍待设计确认。
- 不把 wealth_tier 自动等同于阶级。职业、财富、阶级与 Need Profile 的具体关系应沿用各自语义；不能为了方便把它们合并成同一维度。



标签化需求归属（2026-11-23）
--------------------------
用户确认采用统一 Tag 思路：**万物皆可 Tag 化**。不再把 Need Profile 设计成一种特殊人口实体或必须独立注册的内容类型；人口、商品、需求规则及生产/加工特征均通过 Mod 定义的 Tag 描述和匹配。

设计边界：
- 继续沿用现有 Mod-defined species 人口维度表达种族差异。Engine 不把有机、仿生、合成或机械作为预设人口分类；职业、法律身份、阶级等标签也不能自动替代种族标签。
- 阶级、职业、物种、法律身份等是不同语义的标签/分类，不应互相替代。wealth_tier 也不自动等于阶级。
- Need 规则由 Mod 定义其匹配标签、需求类别、数量需求和可接受/期望档次；Engine 只提供通用匹配、聚合与结算机制。
- 商品可同时携带多个标签。碳水、蛋白质等标签可参与营养/品质计算；建筑/工艺修正与负面加工标签也可参与最终品质。具体 Tag、含义、数值和规则由 Mod INI 提供。
- **Tag 的存在不等于人口份额。** 当前 dimension.<id> 是独立边际比例。若需求规则依赖多个维度的交集，必须由人口数据显式表达该交集人口，不能把独立边际相乘。
- 对需求归属优先研究复用现有 population-group 分类/分布机制表达明确的需求相关人口份额，而不是新增专用 NeedProfile 类型。具体 INI 字段、Tag 结构与匹配运算符尚未最终定稿。
- 多条 Need 规则同时匹配同一人口份额时，必须明确是不同需求类别的累加、修正叠加，还是冲突；不能靠文件顺序或未声明优先级决定。


共享库存分配执行契约：首个 Engine 接口（2026-11-23）
------------------------------------------------------
已实现通用 Mod Effect `colony.stockpile.allocate`：

- Mod 为同一殖民地提交一份完整的 `requests` / `allocations` 计划。请求包含 `id`、`requesterId`、`commodityId` 和 `requested`；分配通过 `requestId` 对应 `allocated`。
- Engine 校验请求 ID 和请求方 ID、商品是否存在、请求与分配是否一一对应，以及是否存在重复/未知/缺失结果、负数、超请求量或超库存分配。
- 整份计划验证完成后才会改写库存。结果包含逐请求的 requested、allocated、unmet、satisfaction，以及逐商品库存扣减前值、扣减量与后值；沿用现有 `mod.effect-applied` 事件记录。
- 同一 Hook 调用中，同一殖民地最多提交一份完整分配计划；多个 Mod 不能依赖加载顺序竞争同一份库存。
- Core 已把现有总人口聚合需求接入该接口。当前 requester 仍是 colony，而不是各 Pop Group；Core 保留现有聚合请求与库存受限分配规则。这只是过渡消费者，不是群体 Tag Need。
- Engine 不设置 pro-rata、平等配给、阶级优先或其他默认分配政策；合法 Mod 结果按原样执行。库存相减仅对 1e-12 相对容差内的负零误差钳制为零，不舍入各请求分配值。
- Tag 匹配运算符、多规则重叠语义、显式联合人口份额与群体级报告仍待设计。独立人口维度不得相乘推导交集人数。

本次只完成共享库存的通用执行机制，不表示需求匹配和群体份额语义已经闭合。


用户最新纠正：Pop Group 按种族区分，不按生命形态硬编码（2026-11-23）
-----------------------------------------------------------------------
前文中“有机 Pop / 仿生 Pop / 机械劳工 Pop 各有固定需求”的设定假设已被用户明确纠正，以上述种族/物种设计为准。此后：
- 种族由 Mod 定义，使用现有 `species` 维度或 Mod 明确声明的其他维度；分类 ID 和含义全部属于 Mod。
- Engine 不建立 organic / synthetic / android / mechanical 的预设分类，不根据名字推断需求。一个种族的需求完全由 Mod 的 Tag / Need 规则决定。
- 当前 Engine 的首个精确匹配机制为单一维度的类别选择：同一维度中多个类别按 OR 合并，人数按该维度显式比例精确计算；未定义该维度的群体返回“维度不存在/未知”，不得视作零人口。
- 多个独立维度的 AND 交集仍不能推导。只有人口数据明确保存联合份额/细分群体后才能匹配；不建立边际乘法或隐藏独立性假设。


Population Tag → 维度类别映射（2026-11-23，第一阶段已实现）
-----------------------------------------------------------
新增 Mod 内容类型 `population_tag`，用途仅是把稳定 Tag ID 映射到现有 Pop Group 的一个统计维度：

```ini
[population_tag.tag.example]
dimension_id = species
category_ids = species-a;species-b
```

并在 Registry 中注册同 ID：

```ini
[entry.tag.example]
type = population_tag
```

契约边界：
- 每个 population Tag 只能指向一个 dimension；`category_ids` 必须非空且不重复。
- 同一 dimension 内列出的 category 是 OR，匹配人口比例为这些互斥类别在该维度中的比例之和。Tag 不创建新人口份额，也不修改 Pop Group。
- Tag 可以映射到 Mod 自定义的任意 dimension/category ID；Engine 不要求它必须叫 `species`，也不内置任何种族或类别名单。
- 若群体不存在目标 dimension，匹配仍是未知；不能当成零。若 dimension 存在但不含所选类别，该类别在该群体的份额为零。
- 一个 population Tag 不能同时要求多个独立 dimension。Need 规则组合多个 Tag 的 AND/OR、跨维度交集、规则重叠/去重、同商品重复需求的语义仍未确定；不得根据独立边际比例相乘。
- 这是人口专用的 Tag 映射适配，不是通用全局 Tag Catalog，也不是 NeedProfile 人口实体。商品等其他对象已有的 `tags` 列表不受影响。

实现落点：Mod Loader 识别 `[population_tag.<id>]`、Registry 识别 `type = population_tag`，Catalog 负责维度与类别 ID 结构校验。定义会传入 Mod 可读取的序列化 Catalog，并参与内容指纹；没有任何人口 Tag 定义时不序列化空集合，保持旧存档内容指纹兼容。此能力尚未被 Core 的具体 Need 规则消费；Core 不添加种族或人口比例。
