Trigger System 与 System Event 架构
=====================================

本文件记录 Trigger System 的 Engine 架构边界。它与玩家可见的事件文本、通知和叙事 UI 分离。

## 概念边界

### Trigger
Trigger 是持久化的单次调度记录。它回答“何时需要处理一次动作”。它不是周期性模拟系统，不是效果本体，也不存放可执行 JS 函数。

### System Event
System Event 是 Trigger 到期时创建的一次性内部处理请求。它包含稳定类型 ID、Trigger ID、来源 Mod、当前 campaign day/date 和 JSON-safe payload。它由 Engine Resolution 接收和处理，处理完成后不作为独立历史保存。

### Resolution
Resolution 是 Engine 注册的同步处理入口。它根据 System Event 类型校验请求、计算/决定结果并调用批准的 Effect/Command/Event 入口。未经注册的 event type 必须拒绝。Mod 不能注册任意 Resolution 函数。

### Effect
Effect 表示经过 Engine 校验的世界状态变化。Trigger 与 Effect 分离：Trigger 负责何时发生，System Event 负责表达一次待处理请求，Resolution 负责执行流程，Effect 负责实际状态变化。

### Domain Event 与 Presentation
Domain Event 是已经发生的事实，存于 `world.domainEvents`，并在世界提交后经只读 Event Bus 发送。它不是待处理请求，也不会自行修改其他子系统状态。
Presentation 以后可以把已提交事实转换为玩家可见通知、报告、文本、图标或弹窗。System Event 本身不要求任何 UI 表现。

## 已确认的调度规则

- Recurring simulation-system cadence 负责重复工作：annual → monthly → weekly → daily；manual 仍仅由显式调用运行。
- Persisted Trigger instance 负责单次日期或经过时间动作，以及以后需要的条件/Domain Event 响应、临时效果到期动作。
- Trigger 使用现有 campaign clock 与 `engine/clock.cjs` 日期规则；不另造日历。
- 当前仅在完整 campaign-day 边界结算，不支持子日触发。
- 每日顺序固定为：推进 campaign clock → 处理此前已到期 Trigger → `campaign.before-day` Hook → recurring simulation systems（annual/monthly/weekly/daily）→ `campaign.after-day` Hook。
- Hook 在当前结算中创建的 Trigger 要等下一个完整日边界处理，避免同一结算内递归触发。
- 到期动作、Domain Event、pending 出队和 receipt 写入都在 detached candidate world 中；整日成功后一起提交，失败则全部回滚。
- Trigger 只能引用已注册且 payload 经验证的 Engine Resolution，不允许任意 JS callback、Mod 任意函数或 world patch。

## 第一阶段实现范围

- World schema 9 新增 `triggerQueue: { pending, receipts }`。
- due kinds 只有 `date`（有效且晚于当前日期的 campaign date）与 `elapsed`（正整数完整游戏日）。
- Hook 返回有限数量的 `triggers`，Owner 由 Engine 注入，ID 必须以 Owner Mod ID 为命名空间前缀。
- 相同 ID + 相同定义去重；相同 ID + 不同定义报错。最近处理回执保留 256 条，回执淘汰后不再保证永久去重。
- 当前唯一 System Event Resolution 为 `effect.apply`，通过现有 `applyModEffect` 执行已批准 Effect；调度时在副本上预验证，到期时重新验证并应用。
- 成功后写入 `mod.effect-applied` 与 `trigger.resolved` Domain Event；只有 world commit 后 Event Bus 才收到事实。

## 明确暂缓

条件/阈值 evaluator、Command Resolution、通用 source/target/operation/value modifier、临时效果状态/到期管理、随机结算池与 UI Presentation 仍属于后续工作。Domain Event 驱动的单次 Trigger 与受限的 `event.emit` Resolution 已落地。每项扩展都必须有真实消费者、明确执行边界和聚焦测试；不为抽象本身堆叠框架。

## Resolution 与 Effect 的执行分离（2026-11-22）

第二阶段将 Resolution 的输出固定为一个受限计划：`{ result, effects }`。

- Resolution 只接收当前 candidate world 的脱离快照，负责读取事件与结算上下文、计算结果并生成 Effect 描述；不得直接修改权威 World。即使 Resolution 修改了自己的快照，该改动也不会提交。
- `result` 是本次结算的 JSON-safe 结果对象，供后续 Domain Event、审计和表现层使用。
- `effects` 是有序的 Effect 描述数组，每项只有稳定类型 ID 与 payload，最多 16 项。
- Trigger Runner 在 Resolution 成功返回并通过计划结构校验后，独立调用 Engine 的 Effect 执行入口；每个 Effect 仍复用已注册的 `applyModEffect` 校验和应用逻辑。
- 每个已执行 Effect 写入标准 `mod.effect-applied` Domain Event；随后写入 `trigger.resolved`，记录 Resolution 结果与实际 Effect 结果。
- Resolution 计算、随机流变化、计算审计、Effect、Domain Event、出队和 receipt 仍全部属于同一个 candidate-world 日结算事务。

当前第二个真实 Resolution 消费者是 `formula.effect`：
- 只允许使用 Engine 已注册的版本化公式，不允许 Mod 注册任意计算函数。
- Formula 输入是调度 Trigger 时捕获的 JSON-safe 快照；到期时不自动重新读取当前世界数据。
- Mod 可声明有限数量的 Effect 模板，并通过 `resultFields` 将公式结果的顶层字段映射到 Effect payload 字段。它不是表达式语言，也不允许覆盖同一模板的静态 payload 字段。
- 随机计算使用从稳定 Trigger ID 派生的命名随机流；计算记录与流状态随 candidate world 一起提交。
- 若公式输出缺少绑定字段、公式输入非法或 Effect 被拒绝，整日 candidate world 回滚，不会出现半完成效果。

本阶段并未增加公式定义、随机事件池、条件表达式、数值 modifier、Command/Event Resolution 或 UI Presentation；只是让现有公式服务成为通用 Resolution 的真实消费者。

## Settlement 执行器与 Trigger Queue 分离（2026-11-22）

新增 `engine/settlement.cjs`，提供共享的 `settleSystemEvent()` 执行管线：

- 输入：一个 System Event、当前 candidate world、注册的 Resolution registry、计算/随机上下文和 Engine Effect executor。
- Resolution 接收 detached world snapshot，返回经过结构校验的 `{ result, effects }` 计划。
- Settlement 依序调用 Effect executor，返回 `{ result, effects: [{ effectType, result }] }`；不修改队列、不写 Domain Event history、不做 UI。
- Trigger Queue 继续负责到期检测、System Event 创建、调用 Settlement、记录 `trigger.resolved`、出队与 receipt。
- Effect executor 仍由 Engine 注入，复用 `applyModEffect` 和现有白名单；Settlement 不接受任意 Mod callback。

这样 Trigger 是一个调度来源，而 Settlement 是可复用的执行管线；其他经批准的 System Event 来源以后可直接复用 Settlement，不必进入 Trigger Queue 内部。

## Domain Event 驱动的单次 Trigger（2026-11-22）

新增 due source：
```js
{
  id: "my-mod.after-market-settlement",
  due: {
    kind: "domain-event",
    type: "market.prices-settled",
    scope: "market",
    subjectId: "my-market"
  },
  event: { type: "effect.apply", payload: { effect: { type: "colony.stability.delta", payload: { colonyId: "my-colony", delta: 2 } } } }
}
```

- `type` 必填；`scope`、`subjectId` 可选，提供时进行精确匹配。不提供 payload 条件表达式、通配符或持续重复订阅。
- 只匹配 Trigger 创建后新写入的 Domain Event；订阅时不扫描既有历史，也不回溯补触发。
- Domain Event emitter 在 candidate world 新增事实时检查当前 pending Trigger。只扫描有上限的待处理队列（最多 4096），不会扫描 Domain Event history，也不依赖其 300 条历史保留窗口。
- 命中后，将完整 JSON-safe source event snapshot 保存到 Trigger，并将 dueDay 设为 source event day + 1。当天只激活、不执行；下一完整日边界由既有 Trigger runner 处理。
- Event Bus 仍只在 world commit 后发布已提交事实；Domain Event-triggered Trigger 在 candidate world 内由 emitter 激活，不把 Event Bus 变为可变状态通道。
- System Event、`trigger.resolved` 和 receipt 保留 sourceEvent 快照；即使 Domain Event history 后续裁剪，Trigger 的来源仍可追溯。
- Duplicate idempotency-key emission 如果返回既有事实，不会再次激活订阅。Time-based Trigger 的既有签名语义不变；本次未升级 world schema。
- 新增单元与集成测试，覆盖精确匹配、source snapshot、下一日结算和既有 Effect/Settlement 执行链。

实现提交：`6804bc9e394abada2dad48dd398fae68636df027`。源码 CI [44957849824](https://github.com/Sakurefa/test-game/actions/runs/44957849824) 成功，223/223 tests、语法检查与 Renderer build 全部通过。


## Resolution 输出 Domain Event（2026-11-22）

新增受限 Resolution：`event.emit`。它补齐的是“已批准的 Engine 结算动作可以产生一个已发生事实”，不是让 Mod/Trigger 直接调用玩家命令或任意事件总线回调。

请求示例：

```js
{
  event: {
    type: "event.emit",
    payload: {
      type: "settlement-finished",
      payload: { settlementId: "my-settlement", outcome: "accepted" }
    }
  }
}
```

- Trigger 所属 Mod 身份由 Engine 从 System Event 的 sourceId 注入；Mod 不能选择另一个 Mod 的来源身份。
- Domain Event 类型自动限定为 `mod.<owner-mod-id>.<type>`，scope 固定为 `mod`，subjectId 固定为 owner Mod ID。输出 payload 自动带入 `modId` 和 `eventType`。
- Resolution 请求只接受自定义类型后缀和 object payload；不接受完整事件 ID、来源身份、scope、subjectId、idempotency key，也不允许发出 Engine 内建事件命名空间。
- Resolution 计划现在可选返回 `domainEvents`，上限 16 条；Effects 仍最多 16 项。Domain Event descriptor 与 Effect descriptor 分开校验。
- Settlement 只验证计划、运行 Effect executor 并返回 Domain Event descriptors；它不写历史、不调 Event Bus。
- Trigger Runner 在同一 candidate-world 事务内先应用 Settlement Effects，再把计划中的 Domain Events 写入事实历史，最后写入 `trigger.resolved`（包含生成事实的 ID/sequence/type 引用）并出队/记 receipt。
- 新事实通过已接入的 candidate-world Domain Event emitter 激活匹配的 pending Trigger；dueDay 是事实日 + 1，因此下一完整日才会执行，当前 due 列表不会递归处理本轮新建的 Trigger。
- 新增测试验证计划校验、输出上限、Settlement 不直接改写 Domain Event history，以及一条完整的 Trigger → event.emit → Domain Event → 另一 Trigger → Effect 链。
- World schema 仍为 9；未加入命令分发器、Mod 任意 callback、Event Bus 写权限或新的持久化队列。

## 现有 Mod Effect 白名单审视（2026-11-22）

当前 `engine/mod-runtime.cjs` 的 `applyModEffect()` 是唯一批准 Mod Effect 的状态转移入口。Hook 返回的 Effects 与 Trigger Resolution 计划中的 Effects 最终复用同一个执行器；Hook 路径和 Trigger 路径都在 candidate world 中执行，并为成功应用的 Effect 写入 `mod.effect-applied`。Trigger 路径还会把本次实际应用结果写入 `trigger.resolved`。整日失败时这些候选变更不会提交。

当前白名单共有 13 种类型：
- Mod 自有状态：`mod.state.set`、`mod.state.increment`、`mod.state.delete`。
- 人口群体：`colony.population.delta`、`colony.population.group.split`、`colony.population.group.merge`、`colony.population.group.dimension.set`。
- 殖民地与市场：`colony.stability.delta`、`colony.stockpile.delta`、`market.price.multiplier`。
- 军事状态：`fleet.readiness.delta`、`fleet.morale.delta`、`war.weariness.delta`。

对仓库当前启用的 Mod 脚本做全文检索，唯一被实际 Mod 内容使用的类型是 `example-market/scripts/market-events.js` 中的 `mod.state.increment`。其他 12 种类型目前由 Effect 执行器、API 契约和测试覆盖，但没有被当前随仓库发布的 Mod 脚本实际调用。它们仍是已公开的 Engine 能力；这项审查不擅自删除或改动其公开类型。

### 当前 Effect 的语义边界

- 白名单中的 Effect 是**立即状态转移请求**：执行时直接改动当前权威 World 字段；修改结果会随正常存档持久化。
- 这些 Effect 不会创建独立的活动效果实例，不保存可供以后移除的来源贡献、叠加关系、持续时间或剩余时间。
- `*.delta` 不是可以安全反向应用的临时 Modifier。例如稳定度先被 +20 后因上限而截断，再于到期时 -20，无法恢复原值；期间其他系统的增减也不能与原 Effect 可靠区分。
- 因此，现有 Trigger Queue 虽能安排未来一次到期动作，却不能自动让现有直接修改型 Effect 变成可撤销的临时效果。临时效果需要独立的、可追踪来源的生命周期状态与明确的应用/移除语义；不能靠保存一个 delta、到期时盲目取反来实现。
- 目前不建设通用 Modifier 语言或活动效果框架。待有真实消费者（例如实际雇佣 workforce 条件、建筑持续加成等）并明确叠加、刷新、覆盖、到期与基础值关系后，再确定最小数据模型。

### Mod 状态增量边界修正（2026-11-22）

`mod.state.increment` 保留现有行为：键不存在时按 0 初始化；键已存在时必须是有限数字。显式 `null` 是合法 JSON 状态值，但不等于键不存在，也不能被静默当作 0。原实现用空值合并导致 `null` 被误判为缺失键；现已改为检查 `Object.hasOwn`，并补入回归测试。


## Trigger 全功能运行验收与缺陷修正（2026-11-22）

### 缺陷与清理

- `engine/triggers.cjs` 原先对 Domain Event source snapshot 复用了 Trigger definition payload 的 16 KiB 上限。Domain Event emitter 本身允许更大的合法 JSON-safe payload，导致同一事实在无监听者时可以写入、有监听 Trigger 时却可能在快照阶段失败。
- 现已将两种数据边界分开：Trigger 自身声明的 Event payload 仍受 16 KiB 限制；Domain Event source snapshot 不再错误套用该限制，完整保留来源事实。回归测试使用 32 KiB payload 验证事实写入与 Trigger 快照均可通过。
- `engine/simulation.cjs` 的 `validateDayInputs()` 与 `processDueTriggers()` 曾对同一 Trigger Queue 重复执行完整校验。日结算入口移除前置重复检查，由 `processDueTriggers()` 在实际处理前统一校验；独立 `validateWorldState()` 仍保留存档/世界边界校验。

### 真实 Mod 运行剧本

- 新增 `tests/fixtures/trigger-test/`，作为 API v4 测试 Mod，不放入正式 `mods/` 目录，不污染 Core 或玩家存档。
