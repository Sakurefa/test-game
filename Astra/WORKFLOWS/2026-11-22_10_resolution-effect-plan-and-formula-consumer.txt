本轮实现
--------
1. Resolution 注册表统一要求返回 `{ result, effects }`。结果对象及每个 Effect 描述均经过 JSON-safe 校验；单个计划最多 16 项 Effect。Resolution 读取当前候选世界的脱离快照，无法通过该引用直接修改权威 candidate world。
2. Trigger Runner 接收 Resolution 计划后，单独调用 Engine 的 Effect 执行入口，按顺序执行已校验 Effect；每个成功应用的 Effect 写入标准 `mod.effect-applied` Domain Event。
3. `trigger.resolved` 记录 Resolution 结果和实际应用的 Effect 结果。计算、随机流状态、计算审计、Effect、Domain Event、出队和 receipt 继续位于同一个 candidate-world 日结算事务内。
4. 原 `effect.apply` 改为返回纯计划，不再直接修改 World；调度和执行阶段仍沿用现有 Effect 校验边界。
5. 新增 `formula.effect` Resolution：只能选择 Engine 已注册的版本化公式，使用调度时捕获的 JSON-safe inputs；按 Trigger ID 派生独立随机流；把公式结果的顶层字段经 `resultFields` 映射到受限 Effect payload。
6. Formula Effect 模板只有稳定 Effect type、静态 payload 和顶层字段映射；不支持表达式、任意 callback、嵌套路径或 Mod 注册公式。效果最终仍由既有 `applyModEffect` 白名单校验与执行。
7. Trigger ID 到随机流 ID 使用可逆、有界编码，保持不同合法 Trigger ID 的独立性；下划线 ID 由集成测试覆盖。

测试覆盖
--------
- Resolution 结果/Effect 分离：resolver 仅看到脱离快照；测试故意修改该快照，确认只有独立 Effect executor 会修改权威 candidate world。
- Resolution 计划结构错误、Effect 描述错误和超过 16 项的计划被拒绝。
- 真实 Mod Hook 安排 `formula.effect`，调用现有 `economy.commodity-price` 公式，并将输出字段应用为所属 Mod 的持久化状态。
- 公式结果、计算审计、Effect 结果、Domain Event 与 Trigger receipt 的一致性。
- 缺少公式输出字段映射时，日结算 candidate world 整体回滚，正式世界、pending Trigger 和 receipt 不变。
- Trigger ID 含下划线时仍生成合法且独立的命名随机流。
- 原日期/经过时间、直接 Effect、失败回滚和去重测试继续保留。
