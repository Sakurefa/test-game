ASTRA WORKING MEMORY
====================

PURPOSE
-------
Help Astra maintain continuity across sessions and execute the user's confirmed direction without expanding scope. This file stores stable agreements, not a live task list.

1. THE USER OWNS THE DIRECTION
------------------------------
- The user defines the game's purpose, priorities, taste and acceptable tradeoffs.
- Astra inspects carefully, explains clearly, implements agreed tasks and reports real results.
- Do not replace the user's direction with a more ambitious architecture.
- “Continue” means continue within confirmed scope; it is not blanket permission for adjacent features or unrelated redesign.
- Do not ask the user to repeat decisions already recorded. Re-read records and verify the repository.

2. THE AK ENGINEERING PRINCIPLE
-------------------------------
- Prefer direct, understandable code: simple, reliable, maintainable and easy to modify.
- Add abstractions only for concrete current consumers.
- Keep the engine generic; game definitions and balance values belong in Mod INI. API v4 JavaScript is for declared behavior hooks, not content replacement.
- Player-visible text belongs in localization INI and definitions reference stable keys.
- Display rounding must not alter calculations or stored inventory.
- Avoid speculative frameworks, recurring full-history audits, self-healing and unnecessary defensive machinery.
- Logs are evidence for external maintenance, not a second authoritative database.

3. COLLABORATION BOUNDARIES
---------------------------
- Inspection is not modification. A finding or recommendation is not approval.
- Do not make unrelated changes.
- Do not claim unperformed features, tests, builds or desktop behavior are verified.
- Keep CI, local checks and user Windows GUI tests separate.
- Preserve existing decisions; raise alternatives as proposals.

4. PROJECT DECISIONS THAT MUST NOT DRIFT
----------------------------------------
- The repository contains complete editable source, Mods, assets and Electron runtime dependencies. The standalone launcher EXE is distributed separately.
- Mod manifests, registry, content definitions and localization remain INI. API v3 INI-only Mods remain supported; API v4 may use explicitly declared JS hooks.
- All runtime game content is supplied by Mods under `mods/`. `mods/core` is the required baseline game-content Mod, not part of the Engine, and cannot be disabled; optional Mods extend or alter game content within Engine contracts.
- Mod scripts receive detached read-only snapshots and return approved effects/events only. Node vm is not a hardened hostile-code security boundary; JS Mods remain trusted/opt-in.
- Keep the engine independent from Electron, DOM and Renderer concerns. Preserve the main-process IPC boundary and atomic day settlement.
- Runtime world state is authoritative; diagnostics are not a transaction-replay database.

5. CONTINUITY AND RECORD KEEPING
--------------------------------
- At task start, follow AGENTS.md and Astra/README.txt; read only discussion topics and workflow records relevant to the task.
- Mandatory engineering principles are maintained in Astra/IMPORTANT_PRINCIPLES/ and must be read before design or implementation. Design discussion is filed by topic in Astra/DISCUSSIONS/. Concrete work sessions are filed in Astra/WORKFLOWS/ using YYYY-MM-DD_NN_work-direction-specific-topic.txt, with one shared chronological sequence per date.
- Root ASTRA_WORKLOG.md is an index/current-state summary, never a chronological transcript.
- Workflow records state baseline/resulting commit, scope, exact files, actual tests/CI, known issues, next user-approved task and Windows GUI status.
- Update topic records when decisions or implementation facts change. Do not create diary filler for routine exchanges.
- Older work queues may be stale; re-check current branch, code and CI.

6. LONG-TERM GAMEPLAY DIRECTION (NOT THE CURRENT ENGINE TASK LIST)
---------------------------------------------------------------------
The long-term game direction includes a Victoria 3-inspired population supply/demand and goods production/consumption economy, alongside the other systems recorded in the design discussions. This is a direction for future game content, not a mandate to implement gameplay content inside the Engine or an approval to invent a finalized rulebook.

The current development stage is building the generic Engine. The Engine provides reusable mechanisms, data loading, validation, scheduling, settlement, persistence and extension contracts. The complete playable game content—including the baseline content—is supplied through Mods under `mods/`. Core is itself the required Mod at `mods/core`; it is not the Engine. Optional Mods can extend or replace content within the Engine's declared contracts.

Need baskets, substitutions, affordability, labor, wages, market clearing, stock allocation and detailed cadence remain open until confirmed. Generic Engine interfaces may support such systems, but concrete definitions, rules and balance values belong to Mod INI.

7. CONFIRMED POPULATION SIMULATION MODEL
----------------------------------------
- Population is aggregate/group-based, not continuously simulated person by person.
- Group attributes initially store aggregate values, averages and proportions, not a full joint distribution.
- Effects and date/condition triggers are separate.
- Needs settle at group level.
- Governing distinction: groups are simulation entities; individuals are narrative entities.
- Named characters may exist for events or unique roles, but must not create individual household/economic simulation or be double-counted in population.
- Dimensions such as class, profession, wealth, species, subspecies and capability are independently extensible and Mod-defined.
- Never infer intersection ratios by multiplying independent marginal proportions; avoid automatic full cross-products.
- Effects use explicit source, target, operation and value where applicable. Temporary effects use separate triggers; process due triggers rather than rescanning all historical effects.
- Do not add personal debt, personal wage ledgers, personal purchases or per-person need settlement to ordinary population runtime.

8. CURRENT ENGINE FOUNDATION GUARDRAIL
---------------------------------------
Continue building Engine capabilities, not a concrete population/economy gameplay feature. The generic aggregate population-group runtime and Mod INI initialization contract are implemented; world save schema is 8.

Each colony retains its compatibility scalar `population` and stores `populationGroups`: stable group IDs, population counts and independent statistical dimensions. Each `dimension.<id>` is a category-to-proportion mapping whose proportions total 1. Group counts must sum to the colony total. Dimensions remain independent marginals; never infer joint ratios by multiplying them or generate a Cartesian product.

Mods may define groups through registered `population_group` content sections with `colony_id`, `population` and optional `dimension.<id>` fields. All enabled-Mod group definitions for one colony must sum to its configured population. Profession and wealth_tier categories resolve against their registered definitions; other dimensions use generic stable IDs. A colony with no Mod-defined groups receives one neutral `unclassified` group. No player-facing localization key is required for these internal initialization records.

The existing `colony.population.delta` effect remains compatible: positive deltas enter `unclassified`; negative deltas reduce all groups proportionally; the total may not become negative. Schema 1–7 saves migrate by creating a neutral group when group data is absent. An empty population-group catalog is omitted from the content fingerprint so unchanged schema-8 saves retain compatibility; actual Mod-defined groups participate in the normal content fingerprint.

No actual demographic composition has been added to Core: new colonies still begin entirely unclassified unless a Mod defines groups. Daily needs continue to settle against scalar colony population, not per group. Do not invent professions, class/wealth distributions, need baskets, wages, employment or market rules. The next unresolved Engine design is how runtime systems should express legitimate group creation, removal, splitting, merging or dimension changes while preserving population totals; clarify semantics before adding mutation APIs or gameplay rules. Keep steps small and consistent with AK and Mod principles.

9. PERSONNEL ENTITIES AND SETTLEMENT-DEPENDENT BUILDING EFFECTS
--------------------------------------------------------------
- Named personnel originate from events. Ordinary hiring may abstract selectable candidates from population groups; special events may create predefined/generated people.
- A separate personnel pool stores acquired people and only the identity, role, capabilities, relationships and affiliations they need.
- Personnel may have class/species/organization affiliation or serve independently. They are not a second population ledger.
- If a person is abstracted from a group, hiring/creation rules must explicitly define whether and when the source group count changes. Never double-count.
- Building conditions use actual employed workforce groups and headcounts, not volatile colony averages or unsupported marginal intersections.
- At configured settlement boundaries, inspect only workforce attributes relevant to active conditions; calculate shares from actual employed headcounts; apply/remove persistent effects; keep effects stable until the next scheduled evaluation.
- Coincident settlement priority is annual → monthly → weekly → daily. Monthly/annual operations are future fixed-date trigger calls, not always-running scans.
- Thresholds, tags, workforce categories, effects and settlement definitions remain Mod-defined INI content.

10. DISCUSSION AND WORKFLOW ARCHIVE RULE
----------------------------------------
- Discussions are organized by subject under Astra/DISCUSSIONS/ and maintained across dates.
- Workflows are organized by date plus concrete work direction/topic under Astra/WORKFLOWS/. A busy day may contain multiple separate records.
- Root ASTRA_WORKLOG.md is a small navigation index, not a transcript.
- Follow Astra/DISCUSSIONS/日志编写规范.txt for naming, daily sequence numbers and cross-links.
